# Upgrade to Veritas features (R-MIG, proposed)

Status: draft for the independent Fred's D49 review. Owner: Fred. Builds on classification.md (CLS-n), debt.md (DEBT-8, GOAL-n), statements.md (ST-n) and actual-format.md. Applies to the wizard that offers to move an Actual budget's own conventions onto Veritas's native features. The R-IDs for it are not in PLAN yet, so the Architect assigns them. Amounts are integer minor units. Examples use made-up names and amounts and a 2-place currency written as `$` unless an example says otherwise, with cents in the data lines.

## MIG-1 The wizard

- **MIG-1.1** **When it is offered.** After an Actual import, once: the first time the imported budget opens with its import finished, a sheet offers it, with "Not now" and "Show me". It records that it was offered (`veritas_meta` key `migration.offered`, value `1`, a settings write that is not an undo step, MIG-1.8), so it never opens by itself again, in this file or after the file is exported and opened again. A budget created in Veritas is never offered it. File, "Upgrade to Veritas features…" opens it at any time, for any budget. With nothing to suggest it says "Nothing to upgrade right now."
- **MIG-1.2** **It only suggests.** Detection reads the budget and writes nothing. Nothing changes until the user ticks an item and confirms on the last step. Closing the sheet, "Not now" or "Cancel" writes nothing except `migration.offered`, which is not an undo step (MIG-1.8).
- **MIG-1.3** **Steps.** (1) Overview: one line per conversion with its count, and the sentence "Nothing changes until you confirm." (2) Review: each suggestion with a checkbox, the signals behind it with their figures ("Why we suggest this"), and "Don't suggest again". (3) Confirm: for each ticked item what will be written, and what will change in reports, with the figures (MIG-2.4). The Apply button is on this step only.
- **MIG-1.4** **Confidence.** Every suggestion has one of three levels, decided by the rules of its conversion:
  - **Pre-ticked**: every signal rule holds, the change is reversible, and nothing the user set is overwritten. The box is ticked, and the user can untick it.
  - **Shown, unticked**: plausible, but it needs the user's judgment, or it needs a figure only the user knows. Unticked, and the sheet's "Select suggested" never ticks it.
  - **Not shown**: the signals are insufficient or conflict. It is not offered, and no name or label alone ever puts a suggestion on screen (CLS-3.4).
- **MIG-1.5** **Apply is one command.** The ticked items are written by one command: one SQLite transaction (R-REL-1) and one undo step (R-REL-5), named "Upgrade to Veritas features". It either writes all of it or none. After it, each converted item has its own "Revert" in the place it lives (MIG-3 to MIG-6), which is its own command and one undo step.
- **MIG-1.6** **Dismissed items.** "Don't suggest again" stores the item's key, `<conversion>:<subject id>` (for example `kind:cat-12`), in the `veritas_meta` row `migration.dismissed`, a JSON array of keys. A dismissed item is not shown again, but the File menu's sheet has "Show dismissed" to bring it back. Suggestions are recomputed every time the sheet opens, so a converted item disappears by itself (its native form now exists) and an item the user changed in Actual since is judged on its new state.
- **MIG-1.7** **No guessing from names.** A name, note wording or label may be shown in the explanation of a suggestion as supporting text. It never makes a suggestion appear, never lifts one from "not shown" to "shown", and never ticks a box: no conversion lets a name do any of these (CLS-3.4). This is checkable: two categories whose figures and rows are identical and whose names differ get the same suggestion, with the same confidence, and only the explanation text differs.
- **MIG-1.8** **Offered, dismissed and not undoable.** Writing `migration.offered` and `migration.dismissed` is a plain settings write. It is not a command and not an undo step, so "Not now" and "Don't suggest again" leave no Undo entry for a sheet the user dismissed. If the session has no settings write outside the undo stack, that is a code requirement of this spec.

## MIG-2 Lossless for Export to Actual

- **MIG-2.1** **Actual's data is left as it is, with these named exceptions.** No conversion writes, edits, deletes or re-files any row of an Actual table: `transactions`, `categories`, `category_groups`, `notes`, `zero_budgets`, `custom_reports`, `dashboard`, `schedules`, `rules`, `payees`, `accounts` and the rest. The only Actual-visible writes are these, each stated on the Confirm step:
  - **(b) the group move** (MIG-4.5): for each adopted goal, `categories.cat_group` and `categories.sort_order` of that category, the `sort_order` of any sibling the move shoves in the Goals group, and, only when the budget has no Goals group, one new `category_groups` row, or, only when the Goals group is hidden, its `category_groups.hidden` set to 0. These are the writes Actual's own move-category and add-group make, so Actual reads the file as if the user had done it there. Actual's budget amounts, transactions and notes are not touched, and every category's own figures and every grand total are unchanged. Only a figure grouped by category group moves with the category.
  - **(b) the opt-in `#goal` line** (MIG-4.5), per goal and off by default: one `notes` line and the per-month `zero_budgets.goal` and `long_goal` figures.
- **MIG-2.2** **Veritas extras ride in `veritas_*` tables**, which Actual ignores and keeps, as goals do (R-GOAL-6). The tables and columns this spec needs are in MIG-7. Exporting to Actual writes the same Actual tables as before. **The precise claim:** after any conversion, every Actual table in the export is row-for-row identical to the export without it, except the writes listed in MIG-2.1. The test (MIG-7.3) lists exactly those columns and rows as the allowed difference, so any other difference fails it.
- **MIG-2.3** **Undo and Revert.** Two things undo a conversion, and they promise different things.
  - **Undo** of the Apply command (one step, MIG-1.5) follows the session's undo model. A row the command changed goes back to its earlier value exactly. A `veritas_*` row the command created is removed. An **Actual row the command created** is not removed: it is left in Actual's retired form, which is the allowed difference after undo (MIG-7.3): a created Goals group is tombstoned, a created note has its text set to NULL and the row stays, and a created `zero_budgets` cell has `budgeted` 0 and `carryover` false and, as a code requirement, `goal` NULL and `long_goal` 0 (the change to `BudgetCell`'s `retired` that this needs, MIG-7.5). Undo lives in memory and is lost when the budget closes.
  - **Revert** of one converted item is a later command, available after a reopen. It restores the item by intent from the stored record of its prior values (MIG-7.1), defined for each conversion in MIG-3.7, MIG-4.7, MIG-5.6 and MIG-6.6. It promises the item's own prior values, not the byte-exact state of every row around it.
- **MIG-2.4** **What changes on screen.** Conversion (c) changes the kind of a category, which reclassifies its past rows (CLS-3.3), so the Confirm step shows the row count and the effect on each report (MIG-5.4). Conversions (a) and (d) change no number in any report, statement or export. Conversion (b) changes no total, but it does change these, and the Confirm step lists them for each goal: a figure grouped by category group follows the category (MIG-4.5a); the Goals screen lists the goal; Wrapped's goals completed and reached months count the goal in the year its backfilled `reached_month` falls in (GOAL-9, FC-8); and the goal's monthly suggestion and ETA appear (DEBT-8.1, FC-6). Hiding or swapping a display never drops history (the principle of CLS-3.2).

## MIG-3 (a) A custom report that imitates a native card

Veritas has native dashboard cards for the figures a hand-built Actual report often rebuilds. This version recognises one: **Net worth** (ST-2). Another card is added only by adding its recognition rule and examples to this section first.

- **MIG-3.1** **Candidates.** A dashboard widget of type `custom-report` (`meta {id}`) on a live dashboard page, whose report is live (`custom_reports` row not tombstoned), has no Veritas override yet (MIG-3.4), and passes the shape test, then the figure test.
- **MIG-3.2** **Shape test (net worth).** All of: `mode = total`; `group_by` is `Account`; `balance_type = Net`; `show_offbudget = 1`; `show_uncategorized = 1`; `conditions` empty, or only `account` conditions (`is`/`oneOf`); the date range reaches back past the first transaction (`date_range = All time`, or a static start on or before the first row) and ends on a date E (the resolved end, for a live range). The graph type is only presentation and does not matter.
- **MIG-3.3** **Figure test (the equivalence).** Equivalent means the figures are equal to the cent, so the shape test is only a filter. The core computes the custom report as Actual would (`customReport`) over its range and compares it with the native Net worth for the same accounts (ST-2: every account in the report's account set, balance on the date). The native figure is ST-2's: it counts closed accounts and deleted accounts that still have live rows, so the comparison never leaves out an account the native card counts. It does this on several dates: E; the last day of the month before E's month, when that is not before the first row; and the last day of the middle month between the month of the first row and E's month, rounded down. For each date D the report is evaluated with its range ending on D. It is equivalent when, on every one of these dates, its total equals the net worth and every account's figure equals that account's balance. Any difference on any date, even 1 cent, means it is not equivalent and is not suggested. Equality on these dates is evidence and not proof for dates in between, so the pre-tick below claims no more than that the two agree on every sampled date and are built the same way.
  - **Pre-ticked** when equivalent and the range is live (`date_static = 0`), because the two stay equal as the date moves.
  - **Shown, unticked** when equivalent but the range is static, because the native card moves with today and the report does not.
  - **Not shown** otherwise.
- **MIG-3.4** **What is written.** One row in `veritas_widget_override` (MIG-7.1): the widget id, the native card type `net-worth-card`, its meta (`name` the report's name, `conditions` and `conditionsOp` copied from the report, `interval` Monthly, `mode` trend), and a fingerprint (MIG-3.8). In Veritas the dashboard slot shows the native card, and the custom report is hidden from Veritas's report list. A "Show hidden reports" toggle lists it.
- **MIG-3.5** **Left untouched.** The `custom_reports` row, the `dashboard` row and the page. Actual still shows the custom report in the same place.
- **MIG-3.8** **The fingerprint.** SHA-256, as lowercase hex, of the UTF-8 bytes of one compact JSON array, `[[report cells],[widget cells]]`, in which a null cell is `null`, an integer cell is its decimal digits, and a text cell is a JSON string escaped as `docs/oracle.md`, "Canonical dump", "Text layout" escapes strings (that escaping only, not the dump's table layout). The two lists are: (1) the report's `custom_reports` row, only the columns that decide its figures, in exactly the order listed here (not the schema's order): `start_date`, `end_date`, `date_static`, `date_range`, `mode`, `group_by`, `balance_type`, `show_empty`, `show_offbudget`, `show_hidden`, `show_uncategorized`, `include_current`, `trim_intervals`, `interval`, `conditions`, `conditions_op`, `metadata` and `tombstone`; (2) the widget's `dashboard` row, only `type` and `meta`. Each JSON column (`conditions`, `metadata`, the widget's `meta`) is parsed and re-encoded with its keys sorted and no insignificant whitespace before it is hashed, so a re-serialised export or import does not change it. JSON that does not parse is hashed as its raw text. The columns left out are `name`, `graph_type`, `sort_by`, `show_trend_lines`, `color_scheme`, `selected_categories` (legacy, Actual moved it into `conditions`) and the widget's position and size (`x`, `y`, `width`, `height`, `dashboard_page_id`): they do not change a figure, so renaming, restyling, moving or resizing in Actual does not undo the swap.
- **MIG-3.6** **Round trip.** The export carries the widget and report exactly as imported. If the report or widget changes in Actual later, the stored fingerprint no longer matches. Veritas then ignores the override, shows the report again, and says "This report changed in Actual, so Veritas shows it again." The stale override row is kept, never deleted by itself.
- **MIG-3.7** **Undo and Revert.** Undo removes the override row (a `veritas_*` row). Revert deletes it too, and the report returns to the slot and the list. Both restore everything, because the conversion wrote nothing else.

## MIG-4 (b) An envelope used as a savings target becomes a Veritas goal

A goal is a category with a `veritas_goal` row, in a Goals group (DEBT-8, R-GOAL-2). This conversion makes the envelope a goal and moves it into the Goals group, as a goal made in Veritas sits there. Money does not move, no budget amount changes, and no transaction is touched. Moving the category is an Actual-visible group change (MIG-2.1).

- **MIG-4.1** **Candidates.** A live, non-hidden, non-archived category with effective kind `expense` (CLS-3.1, never `income`, `debt_principal` or `savings`, because an open goal's category must be `expense`, CLS-3.3), with no `veritas_goal` row, and not a candidate of conversion (c) (MIG-5.5). If the Goals group already holds a live category with the same name, the item cannot be ticked. "The same name" is exactly the comparison the move itself applies when it puts the category in the group (the category-create and move rule, `ensure_free_name`), so a ticked item can never fail Apply on a name; the wizard asks that same predicate and may also treat names that differ only by surrounding spaces as the same. It cannot be ticked because Actual refuses two categories of one name in a group: it shows "Rename one of them first." The same holds between two categories being adopted together: if "Vacation" in Everyday and "Vacation" in Fun are both candidates, the first in Budget screen order can be ticked, and while it is ticked the other shows "Rename one of them first" and cannot be.
- **MIG-4.2** **Signals.**
  - **S1, an explicit target in Actual.** In this order, the first found: `categories.goal_def` with `template_settings.source = 'ui'`; else the category's note with a `#goal <amount>` line, or a `#template <amount> by <month>` line (Actual's `by` and `spend` templates, with no `repeat`), parsed as Actual parses them; else the latest `zero_budgets` month with `long_goal = 1` and its `goal` figure. The target must be above 0 and is on the budget scale (CLS-12.9). Each source has its own unit: a `#goal` or `#template … by` line and a `goal_def` template carry the amount in major units, which Actual converts with `amountToInteger(amount, decimalPlaces)` (`category-template-context.ts` `runGoal`; the UI editors store `integerToAmount`), so `#template 3000 by 2027-06` in a 2-place currency is 300000 and a 0-place `#goal 100000` is 100000. A `zero_budgets.goal` figure is already an integer on the budget scale and is never converted again. **Conflicts:** when two sources give different targets, or different dates, the first in the order above is proposed, but the item is **shown, unticked**, with both figures listed, so the user picks. Sources that agree keep it pre-ticked. For a `by` or `spend` template the target date is the last day of its month. A `#goal` line or `long_goal` figure gives no date. **The line grammar** is Actual's, read from the first `#` of a line, which must be followed by the literal `#goal` or `#template` (case-sensitive, `template-notes.ts:90-93`): `#goal AMOUNT`, and `#template[-PRIORITY] AMOUNT by YYYY-MM`, optionally followed by `spend from YYYY-MM`, never with `repeat`. `AMOUNT` is an optional currency symbol, digits, and optionally a decimal point with one or two digits, with no thousands separators. A line that does not fit is not S1. Templates that budget a monthly amount (`simple`, `periodic`, `schedule`, `remainder`, `average`, `copy`, `percentage`) and a `by` with `repeat` are budgeting rules, not goals, and are not S1.
  - **S2, a steady accumulation.** Over the last 6 complete months before today's month, counting only months not before the budget's first month: at least 4 months have `budgeted > 0`, the largest positive `budgeted` is at most twice the smallest, at most 1 month has spending (CLS-6 `expense_total` above 0 for the category), and `available` at the end of the last complete month is at least twice the median positive `budgeted`. The median is FC-1's: the middle value, or for an even count the two middle values averaged and rounded half away from zero (forecasting.md, "Rounding rules used in this file"). S2 is computed only in a 2-place budget. Where the currency has other than 2 places, `available` mixes two scales (CLS-12.10, D77) and S2 is not evaluated.
  - **S3, a name.** The key (AI-3.6) contains `savings`, `sinking`, `fund`, `emergency`, `vacation`, `holiday`, `trip` or `down payment`. The match is on the key (AI-3.6) of the category's name and of each word, which singularizes both sides, so the words are compared as their keys: `saving`, `sinking`, `fund`, `emergency`, `vacation`, `holiday`, `trip` and `down payment`, and a name matches when its key contains a word's key as whole words in order ("Savings stuff" has the key `saving stuff` and matches `saving`). S3 only ever supplies supporting text (MIG-1.7).
- **MIG-4.3** **Confidence.** **Pre-ticked**: S1 holds. **Shown, unticked**: no S1 but S2 holds (S3 may be shown beside it as supporting text), and the target is left empty. **Not shown**: S3 alone, S2 alone with 2 or more spending months, or anything else.
- **MIG-4.4** **Target and date.** The sheet proposes what S1 gave, and the user confirms or edits both. With S2 and no S1 Veritas invents no target: the field is empty and required, and the Confirm button stays disabled until it holds an amount above 0. The context shown beside it is only the category's own figures, for example "Holds $240.00 now. Budgeted $50.00 in 5 of the last 6 months." No date is proposed without S1.
- **MIG-4.5** **What is written.** For each ticked goal, in the order the Budget screen lists the categories (group order, then category order):
  1. **The Goals group.** The live, non-income group whose trimmed name equals "Goals", case ignored, as a goal made in Veritas finds it. If there is none, one is created named "Goals", after every other group, with the largest live sort order plus 16384, as Actual adds a group. If the group exists but is hidden, the Confirm step says so, and the group is shown again as part of the same command, after the user confirms ('Your group "Goals" is hidden. Show it again and add these goals to it?'). Veritas never creates a second group under another name (CLS-4.1).
  2. **The move.** The category moves to the top of the Goals group (before its first category, as Actual's `moveCategory` does) and keeps its hidden flag. The adopted goals sit above the group's existing categories in the order they had on the Budget screen. Its budget cells, notes and transactions stay with the category.
  3. **The goal row.** One `veritas_goal` row: `target_cents` (budget scale), `target_date` if any, no icon, and `status` by the DEBT-8.2 test (`reached` if `available >= target` for the current month, else `active`), with `reached_month` backfilled as DEBT-8.2 does for imported goals (GOAL-9).
  4. **Actual's representation.** If S1 came from a `#goal` line or from `long_goal` rows, the category already has Actual's goal representation, and DEBT-8's rules for it (the `#goal` line kept when notes are edited) apply from now on. In every other case Actual's notes and `zero_budgets` are not written, unless the user ticks the box below. **Also in Actual, a box per goal, off by default:** "Also show this target in Actual" writes the `#goal <amount>` line and the per-month `goal` and `long_goal` rows as DEBT-8 describes, and the Confirm step states it.
- **MIG-4.5a** **How it round-trips.** The export shows the category in the Goals group, because Actual's own move would write the same rows. Actual's envelope math, budget amounts and every category's own figures are unchanged. A figure grouped by category group (Actual's custom reports grouped by group, Veritas's AI-2.2 group lines, the Sankey's group nodes) moves with the category, and the original group's total falls by what the category held. Grand totals do not change. The original group is left in place even if it is now empty.
- **MIG-4.6** **D77 and the goal rules.** In a budget whose currency does not have 2 places, a goal whose category has recorded spending through the end of the month its line reads gets no suggestion and no ETA, as D77 says, and the adopted goal shows the "spending recorded" lines. Such a category can be adopted only on S1. The goal's monthly suggestion and ETA are computed (DEBT-8.1, FC-6) but never applied, since no budget write is made.
- **MIG-4.7** **Undo and Revert.** The Apply command's undo step restores what it changed, exactly, as MIG-2.3 says: each moved category's group and sort order, each shoved sibling's sort order, an unhidden group's `hidden` flag, and the removal of the `veritas_goal` row. A created Goals group is left tombstoned, and the opt-in note and cells are left in their retired forms (MIG-7.3).
  - **Revert** of one goal works from the record stored in `veritas_migration_applied` (MIG-7.1): the category's original group, the category it sat directly before (its recorded next neighbour: the next category in its original group that the same Apply did not also adopt, so a goal adopted together with the one after it records the first category after both) or "last", and the notes and `zero_budgets` rows this conversion wrote. It works by intent: the category moves back into its recorded group directly before its recorded neighbour, or last in the group if that neighbour is no longer there or no longer in that group. Goals adopted together and adjacent in the original group record the same neighbour, so each returns directly before it. It moves from wherever it is now, even if the user has moved it. The goal row is deleted **only while the goal has not been closed**. Once the goal is closed, its closing, its released leftover and its archive (R-GOAL-5, DEBT-8.3) are the user's own history and Revert is not offered: the item stays in the Upgraded list marked "Closed". An opt-in `#goal` line is removed only if the note is exactly the text the conversion wrote: then Revert removes only the `#goal` line (read from its first `#`) and keeps every other line of the note, and otherwise it leaves the note as it is and says so.
  - **If the original group is gone** (tombstoned or deleted), Revert writes nothing and says "The group {name} no longer exists. Choose a group for {category}.", with a picker of live non-income groups. The category moves when the user picks one.
  - **The opt-in line and cells** are removed only if they are still exactly what this conversion wrote. If the user edited the note or the cell since, Revert leaves it and says so.
  - Revert does not restore the sort orders of siblings that the move shoved, and reverting several goals gives each its recorded neighbour, so the result is the intent and not the byte-exact earlier order. Adjacent goals adopted together all return directly before their shared neighbour, in the order they are reverted, which may differ from their original relative order. Only the Apply's single undo, in the same session with no edits since, restores exactly.

## MIG-5 (c) A category used for debt principal or savings transfers gets its kind

This is the one-time wizard CLS-4.2 promises. Its content is defined here, and CLS-4.2's review count stays.

- **MIG-5.1** **Candidates.** A live category with effective kind `expense` and no `veritas_category_meta.kind`, not an open goal's category (CLS-3.3), and not in an income group. For each, take its rows whose decision is row 8 (a primary on-to-off transfer counted as spending, CLS-4) over the 12 calendar months ending with today's month (the current month counts through today), `T` in number, over `M` distinct calendar months, and let `N` be all its non-mirror classified rows over the same 12 months. Refunds and fees count in `N`.
- **MIG-5.2** **Signals.** The counterparty of a transfer is the off-budget account on its other leg. For the category:
  - **Debt principal** when `T >= 2`, every counterparty is a liability by ST-9.1, and `T` is at least 80% of `N` by count.
  - **Savings** when `T >= 2`, every counterparty is an off-budget asset by ST-9.1 that is not a liability, and `T` is at least 80% of `N`.
  - A category whose counterparties are mixed (some liability, some asset), or whose counterparty is an asset such as a car or a house held for use, with a single transfer, gets no suggestion. A purchase moved into an asset account stays an expense (CLS-4, rows 8 and 9, FIN-2).
- **MIG-5.3** **Confidence.** **Pre-ticked** when the signal holds with `T >= 3`, `M >= 3`, `T` at least 90% of `N`, the category not hidden, and, for savings, every counterparty's Actual account `type` is `savings` or `investment` (the column of docs/actual-format.md, line 181). **Shown, unticked** when the signal holds but any of those stricter conditions does not (for example `T = 2`, a hidden category, or an asset account of another type). **Not shown** otherwise. A category already sharing its kind with a visible category (CLS-4.1) is shown unticked, with "You already use {category} as debt principal."
- **MIG-5.4** **What the Confirm step shows** (CLS-3.3): "{n} rows will change: {t} transfers of {amount} move from spending to debt paydown (or savings), and {p} purchases will be flagged as misfiled." Here `n`, `t`, `{amount}` and `p` count and sum every row of the category in all history, past and future, and not only the 12-month window of the signal, because a kind change reclassifies every row (CLS-3.3). After the change, every transfer is row 6 (`debt_principal`) or row 7 (`savings_contribution`) and every non-transfer purchase in the category is row 14 (`expense`, `misfiled`). `expense_total` falls by the sum of the transfers, `debt_paydown` (or `savings_total`) rises by it, and `net_profit` rises by it. `net_cash_flow` is unchanged, because it is `net_profit - debt_paydown - savings_total`. The Sankey, Wrapped, the forecast baselines and Budget suggestions read the kinds, so they move with it (CLS-7). The sheet shows the figures for the latest complete month.
- **MIG-5.5** **Precedence with (b).** A category that has any row-8 transfer to an off-budget account in the last 12 months is a candidate of (c) only. It is never offered as a goal, because its money leaves the budget, and a goal's category must stay `expense` (CLS-3.3).
- **MIG-5.6** **What is written.** One upsert of `veritas_category_meta.kind` for the category: `debt_principal` or `savings`. Nothing else. Actual's category is unchanged and Actual's own reports are unchanged. **Undo** restores the previous `veritas_category_meta` row exactly. **Revert** restores only the stored `kind`, from the stored record (MIG-7.1), and leaves the row's tax bucket and archive date as they are now. The row is removed only if it ends with no kind, no tax bucket and no archive date. Either way every past figure of the category is restored. A Revert of (c) is itself a kind change on every row of the category, so it always shows the CLS-3.3 confirm first, reversed: "{n} rows will change: {t} transfers of {amount} move from debt paydown (or savings) back to spending, and {p} purchases will no longer be flagged as misfiled", with the effect on each report (MIG-5.4 run the other way), and writes nothing until the user confirms. If the user has set another kind since, the confirm says so and names it before overwriting it. The kind change is a reclassification (CLS-3.3, CLS-4.2), so the reports recompute from the rows, and no row is edited.

## MIG-6 (d) Schedules that are bills get tidied in Bills

- **MIG-6.1** **Candidates.** A live schedule (not tombstoned, not completed) that Bills lists. Settings only Actual understands, meaning a rule with conditions or actions Veritas does not support (R-RULE-3, D2 in contracts/ffi.md v18), are never touched: the migration edits no `schedules` or `rules` row, and the bill stays "read-only, edit in Actual". Its Veritas-only name and icon may still be tidied, and the sheet marks it "has settings only Actual can apply". The wizard's own words never say "rule".
- **MIG-6.2** **Names.** Bills shows `veritas_schedule_meta.display_name`, else the schedule's own `name`, else the payee's name.
  - A schedule with no `name` and a payee gets the payee's name as its proposed display name.
  - When two or more schedules would show the same name, each gets `<name> (<category name>)`, or, when the category is the same or missing, `<name> <n>` by ascending schedule id, `n` starting at 1. Names are compared with the AI-3.6 key.
  - A schedule that already has a `display_name` or a distinct `name` is not renamed.
- **MIG-6.3** **Icons.** An icon (an SF Symbol name or one emoji, validated as a goal's icon is, DEBT-8) is proposed only from structure: `arrow.down.circle` for an income schedule (a positive amount, R-BILL-5), `banknote` for a schedule whose payee is a transfer to a liability account, a loan or a credit card (ST-9.1: an explicit liability kind, loan fields, or a balance below zero). The signal reads "pays {account}, a debt". Every other bill gets none, and the user can pick any icon in the sheet. No icon is proposed from a name.
- **MIG-6.4** **Confidence.** **Pre-ticked**: a proposal that only fills an empty Veritas field (no `display_name` or `icon` yet) and cannot collide. **Shown, unticked**: a proposal that would replace an existing `display_name` or `icon`.
- **MIG-6.5** **What is written.** `veritas_schedule_meta.display_name` and `.icon` (MIG-7.1), which Veritas shows and Actual never sees. Actual's `schedules.name` is not written, because Actual refuses two live schedules with one name, and a Veritas display name must never collide with it. **Also in Actual:** none. A name tidied here shows only in Veritas, which is lossless and not portable, and the sheet says so (decision 3, MIG-9).
- **MIG-6.6** **Round trip, undo and Revert.** The `schedules` and `rules` rows are byte-identical in the export. Undo and Revert restore the prior `display_name` and `icon` of that bill, from the stored record for Revert (a value replaced under MIG-6.4 comes back, and NULL comes back where there was none). They never just clear the columns.

## MIG-7 Contract additions and tests

- **MIG-7.1** **Tables, columns and where they are specified.** All additive.
  - **Tables:** `veritas_widget_override(widget_id TEXT PRIMARY KEY, native_type TEXT, native_meta TEXT JSON, fingerprint TEXT, created_at TEXT)`, and `veritas_migration_applied(item_key TEXT PRIMARY KEY, prior TEXT JSON, applied_at TEXT)`. `prior` holds exactly what that item's Revert restores: for (b) the category's original group id, its next neighbour's id (the next category in that group the same Apply did not also adopt) or null, its original sort order, the created group's id if any, whether the group was unhidden, and the text and cells written for the opt-in line; for (c) the previous `veritas_category_meta` row or null; for (d) the previous `display_name` and `icon`; for (a) nothing. It is written in the Apply transaction.
  - **Columns:** `veritas_schedule_meta.display_name TEXT NULL` and `.icon TEXT NULL`.
  - **Where specified:** the tables and columns go into `contracts/veritas-schema-v1.sql` and `docs/actual-format.md` section 3.12. The new columns go through the store's additive `ALTER TABLE … ADD COLUMN` path and the tables are created if missing, so `schema_version` stays 1 and an older Veritas is not made read-only. `contracts/ffi.md` gets the read and the command.
  - **Settings keys:** `migration.offered` and `migration.dismissed` join the `veritas_meta` keys the user may set (the allowlist in `write.rs`, which refuses others).
  - **The read** `migrationSuggestions(today:)` returns a list of `Suggestion { key, conversion, subject_id, subject_name, confidence (pre_ticked or shown), signals [{ code, text, figures [{ name, value }] }], proposed { target, target_date, kind, display_name, icon, native_type, native_meta }, conflicts, blocked (a reason such as "Rename one of them first", or null), effects [{ report, before, after }] }`.
  - **The command** `applyMigration(selection:)` takes `Selection { items [{ key, edits }], consent_show_goals_group }`. `edits` carries every value the user edited: for (b) `target` (budget scale) and `target_date`, and `write_note_in_actual` (the per-goal box); for (c) `kind`; for (d) `display_name` and `icon`. `consent_show_goals_group` is the user's yes to showing a hidden Goals group again. An item key that is no longer a suggestion, or a blocked one, makes the whole command fail with nothing written.
- **MIG-7.2** **Detection is pure.** `migrationSuggestions` writes nothing and is deterministic for a given budget and date.
- **MIG-7.3** **Lossless test.** For each example below, export to Actual before and after `applyMigration` and compare every non-`veritas_*` table row for row. The allowed difference is exactly the writes of MIG-2.1: the moved categories' `cat_group` and `sort_order`, shoved siblings' `sort_order`, a created or unhidden Goals group, and, for a goal whose box is ticked, its `notes` line and `zero_budgets` figures. Any other difference fails. Then undo and compare every table again with its state before Apply. After undo, rows the command changed are identical, `veritas_*` rows it created are gone, and the only allowed difference is the **retired form of an Actual row the command created**: a created Goals group is tombstoned (it is still in `category_groups`, with `tombstone` 1), a created note row remains with its text NULL, and a created `zero_budgets` cell remains with `budgeted` 0, `carryover` 0, `goal` NULL and `long_goal` 0. Any other difference fails.

- **MIG-7.4** **Revert tests.** After a reopen, each Revert restores from `veritas_migration_applied` alone. A Revert of (c) shows the reversed CLS-3.3 confirm with the row counts and report effects and writes nothing until confirmed: with the 3 transfers of example 10 it reads "3 rows will change: 3 transfers of 1,156.50 move from debt paydown back to spending". Cases: the category returns before its recorded neighbour; the neighbour is gone, so it goes last; the original group is gone, so Revert writes nothing and asks; a value replaced under MIG-6.4 comes back; two goals adopted then reverted in either order each land before their own recorded neighbour. **Adjacent pair:** in Everyday the order is X, A, B, C and A and B are adopted together. Both record neighbour C (the next category the Apply did not adopt), not each other. Reverting A first, then B, or B first, then A, returns both directly before C (X, then A and B in the order reverted, then C), and neither goes last.
- **MIG-7.5** **Code requirement.** `BudgetCell`'s `retired` form must clear `goal` and `long_goal`, so that undoing a created cell leaves no goal figure behind (MIG-2.3, MIG-7.3).
