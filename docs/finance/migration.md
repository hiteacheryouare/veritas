# Upgrade to Veritas features (R-MIG, proposed)

Status: draft for the independent Fred's D49 review. Owner: Fred. Builds on classification.md (CLS-n), debt.md (DEBT-8, GOAL-n), statements.md (ST-n) and actual-format.md. Applies to the wizard that offers to move an Actual budget's own conventions onto Veritas's native features. The R-IDs for it are not in PLAN yet, so the Architect assigns them. Amounts are integer minor units. Examples use made-up names and amounts and a 2-place currency written as `$` unless an example says otherwise, with cents in the data lines.

## MIG-1 The wizard

- **MIG-1.1** **When it is offered.** After an Actual import, once: the first time the imported budget opens with its import finished, a sheet offers it, with "Not now" and "Show me". It records that it was offered (`veritas_meta` key `migration.offered`, value `1`), so it never opens by itself again, in this file or after the file is exported and opened again. A budget created in Veritas is never offered it. File, "Upgrade to Veritas features…" opens it at any time, for any budget. With nothing to suggest it says "Nothing to upgrade right now."
- **MIG-1.2** **It only suggests.** Detection reads the budget and writes nothing. Nothing changes until the user ticks an item and confirms on the last step. Closing the sheet, "Not now" or "Cancel" writes nothing except `migration.offered`.
- **MIG-1.3** **Steps.** (1) Overview: one line per conversion with its count, and the sentence "Nothing changes until you confirm." (2) Review: each suggestion with a checkbox, the signals behind it with their figures ("Why we suggest this"), and "Don't suggest again". (3) Confirm: for each ticked item what will be written, and what will change in reports, with the figures (MIG-2.4). The Apply button is on this step only.
- **MIG-1.4** **Confidence.** Every suggestion has one of three levels, decided by the rules of its conversion:
  - **Pre-ticked**: every signal rule holds, the change is reversible, and nothing the user set is overwritten. The box is ticked, and the user can untick it.
  - **Shown, unticked**: plausible, but it needs the user's judgment, or it needs a figure only the user knows. Unticked, and the sheet's "Select suggested" never ticks it.
  - **Not shown**: the signals are insufficient or conflict. It is not offered, and no name or label alone ever puts a suggestion on screen (CLS-3.4).
- **MIG-1.5** **Apply is one command.** The ticked items are written by one command: one SQLite transaction (R-REL-1) and one undo step (R-REL-5), named "Upgrade to Veritas features". It either writes all of it or none. After it, each converted item has its own "Revert" in the place it lives (MIG-3 to MIG-6), which is its own command and one undo step.
- **MIG-1.6** **Dismissed items.** "Don't suggest again" stores the item's key, `<conversion>:<subject id>` (for example `kind:cat-12`), in the `veritas_meta` row `migration.dismissed`, a JSON array of keys. A dismissed item is not shown again, but the File menu's sheet has "Show dismissed" to bring it back. Suggestions are recomputed every time the sheet opens, so a converted item disappears by itself (its native form now exists) and an item the user changed in Actual since is judged on its new state.
- **MIG-1.7** **No guessing from names.** A name, note wording or label may be shown in the explanation of a suggestion, and may lift a suggestion from "not shown" to "shown, unticked" only where a conversion says so. It never counts as a signal that ticks a box (CLS-3.4).

## MIG-2 Lossless for Export to Actual

- **MIG-2.1** **Actual's data is left as it is, with these named exceptions.** No conversion writes, edits, deletes or re-files any row of an Actual table: `transactions`, `categories`, `category_groups`, `notes`, `zero_budgets`, `custom_reports`, `dashboard`, `schedules`, `rules`, `payees`, `accounts` and the rest. The only Actual-visible writes are these, each stated on the Confirm step:
  - **(b) the group move** (MIG-4.5): for each adopted goal, `categories.cat_group` and `categories.sort_order` of that category, the `sort_order` of any sibling the move shoves in the Goals group, and, only when the budget has no Goals group, one new `category_groups` row, or, only when the Goals group is hidden, its `category_groups.hidden` set to 0. These are the writes Actual's own move-category and add-group make, so Actual reads the file as if the user had done it there. Actual's budget amounts, transactions and notes are not touched, and every category's own figures and every grand total are unchanged. Only a figure grouped by category group moves with the category.
  - **(b) the opt-in `#goal` line** (MIG-4.5), per goal and off by default: one `notes` line and the per-month `zero_budgets.goal` and `long_goal` figures.
- **MIG-2.2** **Veritas extras ride in `veritas_*` tables**, which Actual ignores and keeps, as goals do (R-GOAL-6). The tables and columns this spec needs are in MIG-7. Exporting to Actual writes the same Actual tables as before. **The precise claim:** after any conversion, every Actual table in the export is row-for-row identical to the export without it, except the writes listed in MIG-2.1. The test (MIG-7.3) lists exactly those columns and rows as the allowed difference, so any other difference fails it.
- **MIG-2.3** **Undo.** Each conversion can be undone exactly: the undo step restores the `veritas_*` rows to their earlier state (absent rows removed, changed rows put back). A "Revert" on a converted item does the same for that item alone.
- **MIG-2.4** **Only (c) changes a reported figure.** Conversion (c) changes the kind of a category, which reclassifies its past rows (CLS-3.3), so the Confirm step shows the row count and the effect on each report (MIG-5.4). Conversions (a) and (d) change no number in any report, statement or export. Conversion (b) changes none either, except a figure grouped by category group, which follows the category (MIG-4.5a). Hiding or swapping a display never drops history (the principle of CLS-3.2).

## MIG-3 (a) A custom report that imitates a native card

Veritas has native dashboard cards for the figures a hand-built Actual report often rebuilds. This version recognises one: **Net worth** (ST-2). Another card is added only by adding its recognition rule and examples to this section first.

- **MIG-3.1** **Candidates.** A dashboard widget of type `custom-report` (`meta {id}`) on a live dashboard page, whose report is live (`custom_reports` row not tombstoned), has no Veritas override yet (MIG-3.4), and passes the shape test, then the figure test.
- **MIG-3.2** **Shape test (net worth).** All of: `mode = total`; `group_by` is `Account`; `balance_type = Net`; `show_offbudget = 1`; `show_uncategorized = 1`; `conditions` empty, or only `account` conditions (`is`/`oneOf`); the date range reaches back past the first transaction (`date_range = All time`, or a static start on or before the first row) and ends on a date E (the resolved end, for a live range). The graph type is only presentation and does not matter.
- **MIG-3.3** **Figure test (the equivalence).** Equivalent means the figures are equal to the cent, so the shape test is only a filter. The core computes the custom report as Actual would (`customReport`) over its range and compares it with the native Net worth for the same accounts at E (ST-2: every account in the report's account set, balance on E). The report is equivalent when its total equals the net worth, and every account's figure equals that account's balance on E. Any difference, even 1 cent, means it is not equivalent and is not suggested.
  - **Pre-ticked** when equivalent and the range is live (`date_static = 0`), because the two stay equal as the date moves.
  - **Shown, unticked** when equivalent but the range is static, because the native card moves with today and the report does not.
  - **Not shown** otherwise.
- **MIG-3.4** **What is written.** One row in `veritas_widget_override` (MIG-7.1): the widget id, the native card type `net-worth-card`, its meta (`name` the report's name, `conditions` and `conditionsOp` copied from the report, `interval` Monthly, `mode` trend), and a fingerprint of the custom report's row and the widget's row. In Veritas the dashboard slot shows the native card, and the custom report is hidden from Veritas's report list. A "Show hidden reports" toggle lists it.
- **MIG-3.5** **Left untouched.** The `custom_reports` row, the `dashboard` row and the page. Actual still shows the custom report in the same place.
- **MIG-3.6** **Round trip.** The export carries the widget and report exactly as imported. If the report or widget changes in Actual later, the stored fingerprint no longer matches. Veritas then ignores the override, shows the report again, and says "This report changed in Actual, so Veritas shows it again." The stale override row is kept, never deleted by itself.
- **MIG-3.7** **Undo and revert.** Delete the override row. The report returns to the slot and the list.

## MIG-4 (b) An envelope used as a savings target becomes a Veritas goal

A goal is a category with a `veritas_goal` row, in a Goals group (DEBT-8, R-GOAL-2). This conversion makes the envelope a goal and moves it into the Goals group, as a goal made in Veritas sits there. Money does not move, no budget amount changes, and no transaction is touched. Moving the category is an Actual-visible group change (MIG-2.1).

- **MIG-4.1** **Candidates.** A live, non-hidden, non-archived category with effective kind `expense` (CLS-3.1, never `income`, `debt_principal` or `savings`, because an open goal's category must be `expense`, CLS-3.3), with no `veritas_goal` row, and not a candidate of conversion (c) (MIG-5.5). If the Goals group already holds a live category with the same name (case ignored), the item cannot be ticked, because Actual refuses two categories of one name in a group: it shows "Rename one of them first."
- **MIG-4.2** **Signals.**
  - **S1, an explicit target in Actual.** In this order, the first found: `categories.goal_def` with `template_settings.source = 'ui'`; else the category's note with a `#goal <amount>` line, or a `#template <amount> by <month>` line (Actual's `by` and `spend` templates, with no `repeat`), parsed as Actual parses them; else the latest `zero_budgets` month with `long_goal = 1` and its `goal` figure. The target is the amount, converted to the budget scale (CLS-12.9) by the currency's places, and must be above 0. For a `by` or `spend` template the target date is the last day of its month. A `#goal` line or `long_goal` figure gives no date. Templates that budget a monthly amount (`simple`, `periodic`, `schedule`, `remainder`, `average`, `copy`, `percentage`) and a `by` with `repeat` are budgeting rules, not goals, and are not S1.
  - **S2, a steady accumulation.** Over the last 6 complete months before today's month, counting only months not before the budget's first month: at least 4 months have `budgeted > 0`, the largest positive `budgeted` is at most twice the smallest, at most 1 month has spending (CLS-6 `expense_total` above 0 for the category), and `available` at the end of the last complete month is at least twice the median positive `budgeted`. S2 is computed only in a 2-place budget. Where the currency has other than 2 places, `available` mixes two scales (CLS-12.10, D77) and S2 is not evaluated.
  - **S3, a name.** The key (AI-3.6) contains `savings`, `sinking`, `fund`, `emergency`, `vacation`, `holiday`, `trip` or `down payment`. It is only ever a supporting signal (MIG-1.7).
- **MIG-4.3** **Confidence.** **Pre-ticked**: S1 holds. **Shown, unticked**: no S1 but S2 holds (S3 may be shown beside it as supporting text), and the target is left empty. **Not shown**: S3 alone, S2 alone with 2 or more spending months, or anything else.
- **MIG-4.4** **Target and date.** The sheet proposes what S1 gave, and the user confirms or edits both. With S2 and no S1 Veritas invents no target: the field is empty and required, and the Confirm button stays disabled until it holds an amount above 0. The context shown beside it is only the category's own figures, for example "Holds $240.00 now. Budgeted $50.00 in 5 of the last 6 months." No date is proposed without S1.
- **MIG-4.5** **What is written.** For each ticked goal, in the order the Budget screen lists the categories (group order, then category order):
  1. **The Goals group.** The live, non-income group whose trimmed name equals "Goals", case ignored, as a goal made in Veritas finds it. If there is none, one is created named "Goals", after every other group, with the largest live sort order plus 16384, as Actual adds a group. If the group exists but is hidden, the Confirm step says so, and the group is shown again as part of the same command, after the user confirms ('Your group "Goals" is hidden. Show it again and add these goals to it?'). Veritas never creates a second group under another name (CLS-4.1).
  2. **The move.** The category moves to the top of the Goals group (before its first category, as Actual's `moveCategory` does) and keeps its hidden flag. The adopted goals sit above the group's existing categories in the order they had on the Budget screen. Its budget cells, notes and transactions stay with the category.
  3. **The goal row.** One `veritas_goal` row: `target_cents` (budget scale), `target_date` if any, no icon, and `status` by the DEBT-8.2 test (`reached` if `available >= target` for the current month, else `active`), with `reached_month` backfilled as DEBT-8.2 does for imported goals (GOAL-9).
  4. **Actual's representation.** If S1 came from a `#goal` line or from `long_goal` rows, the category already has Actual's goal representation, and DEBT-8's rules for it (the `#goal` line kept when notes are edited) apply from now on. In every other case Actual's notes and `zero_budgets` are not written, unless the user ticks the box below. **Also in Actual, a box per goal, off by default:** "Also show this target in Actual" writes the `#goal <amount>` line and the per-month `goal` and `long_goal` rows as DEBT-8 describes, and the Confirm step states it.
- **MIG-4.5a** **How it round-trips.** The export shows the category in the Goals group, because Actual's own move would write the same rows. Actual's envelope math, budget amounts and every category's own figures are unchanged. A figure grouped by category group (Actual's custom reports grouped by group, Veritas's AI-2.2 group lines, the Sankey's group nodes) moves with the category, and the original group's total falls by what the category held. Grand totals do not change. The original group is left in place even if it is now empty.
- **MIG-4.6** **D77 and the goal rules.** In a budget whose currency does not have 2 places, a goal whose category has recorded spending through the end of the month its line reads gets no suggestion and no ETA, as D77 says, and the adopted goal shows the "spending recorded" lines. Such a category can be adopted only on S1. The goal's monthly suggestion and ETA are computed (DEBT-8.1, FC-6) but never applied, since no budget write is made.
- **MIG-4.7** **Undo and revert.** The undo step restores exactly what the command changed. Before it writes, the command records the prior value of every row it will change: each moved category's group and sort order, each shoved sibling's sort order, a created group (removed again on undo, as undo of any created row is), and an unhidden group's `hidden` flag. Undo puts those values back, so the category returns to its original group at its original position, and the Goals group returns to its original order and visibility. It also removes the `veritas_goal` row and, with the box ticked, only the line and rows this conversion added. A goal's own "Revert" does the same for that goal alone, in the same order (so reverting several goals in any order restores the group exactly, because each restores its own recorded values).

## MIG-5 (c) A category used for debt principal or savings transfers gets its kind

This is the one-time wizard CLS-4.2 promises. Its content is defined here, and CLS-4.2's review count stays.

- **MIG-5.1** **Candidates.** A live category with effective kind `expense` and no `veritas_category_meta.kind`, not an open goal's category (CLS-3.3), and not in an income group. For each, take its rows whose decision is row 8 (a primary on-to-off transfer counted as spending, CLS-4) over the last 12 months, `T` in number, over `M` distinct calendar months, and let `N` be all its non-mirror classified rows over the same 12 months. Refunds and fees count in `N`.
- **MIG-5.2** **Signals.** The counterparty of a transfer is the off-budget account on its other leg. For the category:
  - **Debt principal** when `T >= 2`, every counterparty is a liability by ST-9.1, and `T` is at least 80% of `N` by count.
  - **Savings** when `T >= 2`, every counterparty is an off-budget asset by ST-9.1 that is not a liability, and `T` is at least 80% of `N`.
  - A category whose counterparties are mixed (some liability, some asset), or whose counterparty is an asset such as a car or a house held for use, with a single transfer, gets no suggestion. A purchase moved into an asset account stays an expense (CLS-4, rows 8 and 9, FIN-2).
- **MIG-5.3** **Confidence.** **Pre-ticked** when the signal holds with `T >= 3`, `M >= 3`, `T` at least 90% of `N`, the category not hidden, and, for savings, every counterparty's Actual account `type` is `savings` or `investment` (the column of docs/actual-format.md, line 181). **Shown, unticked** when the signal holds but any of those stricter conditions does not (for example `T = 2`, a hidden category, or an asset account of another type). **Not shown** otherwise. A category already sharing its kind with a visible category (CLS-4.1) is shown unticked, with "You already use {category} as debt principal."
- **MIG-5.4** **What the Confirm step shows** (CLS-3.3): "{n} rows will change: {t} transfers of {amount} move from spending to debt paydown (or savings), and {p} purchases will be flagged as misfiled." After the change, every transfer is row 6 (`debt_principal`) or row 7 (`savings_contribution`) and every non-transfer purchase in the category is row 14 (`expense`, `misfiled`). `expense_total` falls by the sum of the transfers, `debt_paydown_total` (or `savings_total`) rises by it, and `net_profit` rises by it. `net_cash_flow` is unchanged, because it is `net_profit - debt_paydown - savings_total`. The Sankey, Wrapped, the forecast baselines and Budget suggestions read the kinds, so they move with it (CLS-7). The sheet shows the figures for the latest complete month.
- **MIG-5.5** **Precedence with (b).** A category that has any row-8 transfer to an off-budget account in the last 12 months is a candidate of (c) only. It is never offered as a goal, because its money leaves the budget, and a goal's category must stay `expense` (CLS-3.3).
- **MIG-5.6** **What is written.** One upsert of `veritas_category_meta.kind` for the category: `debt_principal` or `savings`. Nothing else. Actual's category is unchanged and Actual's own reports are unchanged. **Revert** restores the previous `veritas_category_meta` row (or removes it), which restores every past figure. The kind change is a reclassification (CLS-3.3, CLS-4.2), so the reports recompute from the rows, and no row is edited.

## MIG-6 (d) Schedules that are bills get tidied in Bills

- **MIG-6.1** **Candidates.** A live schedule (not tombstoned, not completed) that Bills lists. Settings only Actual understands, meaning a rule with conditions or actions Veritas does not support (R-RULE-3, D2 in contracts/ffi.md v18), are never touched: the migration edits no `schedules` or `rules` row, and the bill stays "read-only, edit in Actual". Its Veritas-only name and icon may still be tidied, and the sheet marks it "has settings only Actual can apply". The wizard's own words never say "rule".
- **MIG-6.2** **Names.** Bills shows `veritas_schedule_meta.display_name`, else the schedule's own `name`, else the payee's name.
  - A schedule with no `name` and a payee gets the payee's name as its proposed display name.
  - When two or more schedules would show the same name, each gets `<name> (<category name>)`, or, when the category is the same or missing, `<name> <n>` by ascending schedule id, `n` starting at 1. Names are compared with the AI-3.6 key.
  - A schedule that already has a `display_name` or a distinct `name` is not renamed.
- **MIG-6.3** **Icons.** An icon (an SF Symbol name or one emoji, validated as a goal's icon is, DEBT-8) is proposed only from structure: `arrow.down.circle` for an income schedule (a positive amount, R-BILL-5), `banknote` for a schedule whose payee is a transfer to a loan account. Every other bill gets none, and the user can pick any icon in the sheet. No icon is proposed from a name.
- **MIG-6.4** **Confidence.** **Pre-ticked**: a proposal that only fills an empty Veritas field (no `display_name` or `icon` yet) and cannot collide. **Shown, unticked**: a proposal that would replace an existing `display_name` or `icon`.
- **MIG-6.5** **What is written.** `veritas_schedule_meta.display_name` and `.icon` (MIG-7.1), which Veritas shows and Actual never sees. Actual's `schedules.name` is not written, because Actual refuses two live schedules with one name, and a Veritas display name must never collide with it. **Also in Actual:** none. A name tidied here shows only in Veritas, which is lossless and not portable, and the sheet says so (decision 3, MIG-9).
- **MIG-6.6** **Round trip and undo.** The `schedules` and `rules` rows are byte-identical in the export. Revert clears the two columns for that bill.

## MIG-7 Contract additions and tests

- **MIG-7.1** **Tables and columns.** All additive (contracts/ffi.md changelog, a new version): table `veritas_widget_override(widget_id PK, native_type, native_meta JSON, fingerprint, created_at)`; columns `veritas_schedule_meta.display_name TEXT NULL` and `.icon TEXT NULL`; the `veritas_meta` keys `migration.offered` and `migration.dismissed`. A read `migrationSuggestions(today:)` returns the suggestions with their signals and confidence, and a command `applyMigration(selection:)` applies them (MIG-1.5). Neither is wired to a screen by this spec.
- **MIG-7.2** **Detection is pure.** `migrationSuggestions` writes nothing and is deterministic for a given budget and date.
- **MIG-7.3** **Lossless test.** For each example below, export to Actual before and after `applyMigration` and compare every non-`veritas_*` table row for row. The allowed difference is exactly the writes of MIG-2.1: the moved categories' `cat_group` and `sort_order`, shoved siblings' `sort_order`, a created or unhidden Goals group, and, for a goal whose box is ticked, its `notes` line and `zero_budgets` figures. Any other difference fails. Then undo and compare the `veritas_*` tables with their state before.

## MIG-8 Worked examples (tests)

Today is 2026-11-22 unless an example says otherwise.

1. **(a) Net worth report, equivalent.** Accounts on 2026-11-22: Checking 200000, Savings 500000, Visa -30000 (on budget), Car Loan -980000 (off budget), Brokerage 1000000 (off budget). Net worth = 200000 + 500000 - 30000 - 980000 + 1000000 = 690000. The custom report "Net worth": `mode total`, `group_by Account`, `balance_type Net`, `show_offbudget 1`, `show_uncategorized 1`, no conditions, `date_range All time`, `date_static 0`. It totals 690000 and each account matches its balance, so it is equivalent, live, and **pre-ticked**. Writes one `veritas_widget_override` row. Actual still shows the report.
2. **(a) Not equivalent.** The same report with `show_offbudget 0` totals 200000 + 500000 - 30000 = 670000, not 690000. It is not suggested. With `show_uncategorized 0` and an uncategorized row of -5000 in Checking, the total differs by 5000 and it is not suggested.
3. **(a) Static range.** The first report with `date_static 1`, `end_date 2026-06-30`, and net worth on that date 640000 equal to the report's total: **shown, unticked**.
4. **(a) Changed in Actual.** After example 1 is applied, the user edits the report in Actual (adds a condition). The fingerprint differs. Veritas ignores the override and shows the report again with the notice.
5. **(b) S1 with a date.** "Vacation" has the note `#template 3000 by 2027-06`. Target 300000 (budget scale, 2 places), date 2027-06-30. `available` for November 2026 is 120000 and November's `budgeted` is 0, below the target, so `status active`. **Pre-ticked.** The DEBT-8.1 suggestion for the goal: months left from November 2026 through June 2027 is 8 (November to June, both counted). Carry is `available - budgeted(M)` = 120000 - 0 = 120000, `remaining = 300000 - 120000 = 180000`, `monthly = ceil(180000 / 8) = 22500`. Not applied.
6. **(b) S1, no date.** "Emergency" has the note `#goal 10000`. Target 1000000, no date. **Pre-ticked.** Actual already has the `#goal` line, so DEBT-8's note rules apply from now on.
7. **(b) S2 only.** "Car repairs" is budgeted 5000 in 5 of the last 6 complete months (May to October 2026, with 0 in July), no spending, and `available` at the end of October is 25000. Largest 5000 is at most twice the smallest 5000. `available` 25000 is at least twice the median budgeted 5000 (10000). S2 holds, no S1. **Shown, unticked**, target empty and required.
8. **(b) Not shown.** "Dining" is budgeted 30000 each month and spends 28000 most months: more than 1 spending month, so S2 fails. A category called "Savings stuff" with no accumulation and no template has S3 alone. Neither is shown.
9. **(b) A budget without 2 places.** A yen budget: "Trip" with `#goal 100000` (budget scale, so ¥100,000) is S1 and **pre-ticked**. "Rice fund" with only a steady budget has no S1, and S2 is not evaluated, so it is not shown. If "Trip" has spending through the end of the month, the adopted goal shows "spending recorded" and no suggestion (D77).
10. **(c) Debt principal.** "Car Loan" has transfers of -38550 on 2026-08-20, 2026-09-20 and 2026-10-20 to Car Loan (off budget, kind Liability), nothing else. `T = 3`, `M = 3`, `T/N = 100%`: **pre-ticked** debt principal. Effect on October, with income 310000 and expenses before 120000: Net Profit 310000 - 120000 = 190000. After: expenses 120000 - 38550 = 81450, debt paydown 38550, Net Profit 310000 - 81450 = 228550. Net cash flow before 190000 - 0 - 0 = 190000, after 228550 - 38550 - 0 = 190000, unchanged. The Confirm step reads "3 rows will change: 3 transfers of 385.50 move from spending to debt paydown."
11. **(c) Savings.** "Emergency Fund" has transfers of -25000 to Brokerage (off budget, an asset, Actual `type investment`) in each of August, September and October. **Pre-ticked** savings. With the Brokerage's `type` unset it is **shown, unticked**.
12. **(c) No suggestion.** A "Car" category with one transfer of -50000 to a Car asset account: `T = 1`, no suggestion. A category called "Loan Principal" with no transfers: no suggestion (CLS-3.4). A category with 2 transfers to a loan and 2 to a savings account: mixed, no suggestion.
13. **(c) vs (b).** "Emergency Fund" is also steady and accumulating (S2) and has the transfers of example 11. It is a candidate of (c) only (MIG-5.5).
14. **(d) Names.** A schedule with no `name`, payee "Netflix": proposed display name "Netflix", **pre-ticked**. Two schedules with no `name`, both payee "Gym", categories Fitness and Health: "Gym (Fitness)" and "Gym (Health)". Two with no `name`, payee "Gym", the same category, ids `s1` and `s2`: "Gym 1" and "Gym 2". A schedule named "Rent" is left alone.
15. **(d) Settings only Actual understands.** A schedule whose rule has an action Veritas does not support: its `schedules` and `rules` rows are untouched, it is marked "has settings only Actual can apply", and a display name from its payee may still be proposed.
16. **(d) Icons.** An income schedule (+310000) gets `arrow.down.circle`, a payment to the Car Loan account gets `banknote`, a "Gym" bill gets none.
17. **Apply and undo.** The user ticks examples 1, 5, 10 and 14 and confirms.
