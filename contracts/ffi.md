# FFI surface (contract v11)

`veritas-ffi` is the only crate the apps link. It exports with UniFFI proc macros, and `cargo xtask bindings` generates the Swift module `VeritasCore`, with its C module `VeritasCoreFFI`, into `apps/macos/Packages/VeritasKit`. Swift never sees SQL, Actual column names or business rules (PLAN §6.1, Appendix C).

## Rules for every export

- Every export returns `Result<_, FfiError>` and goes through `guard`, which catches panics into `FfiError::Internal`. UniFFI turns an infallible export into `try!` in Swift, so a panic there would crash the app.
- Coarse calls only. The UI asks for whole screen models ("budget month 2027-03"), never one cell at a time (PLAN §6.5).
- Records are plain data. Money crosses as `i64` minor units, and VeritasKit formats it for display. v11: some widget values cross as `f64` minor units, where Actual's own figure is fractional or can be NaN or infinite (the summary card, the crossover card, the spending card's budget line and the Monte Carlo card); the shell rounds them only for display. Dates cross as `"YYYY-MM-DD"` strings, months as `Month`, and moments as UTC `"YYYY-MM-DDTHH:MM:SSZ"`.
- Long work (open, create, import, export, and later reports and forecasts) is `async` in Swift, runs on a core thread, and takes a `CancelToken`. UniFFI never cancels the Rust side of an `async` call, so cancelling the Swift task alone stops nothing. The caller makes a `CancelToken()` per call and calls `token.cancel()` from `withTaskCancellationHandler`. The work then stops before its one visible step: a cancelled create, import or export leaves nothing behind, and a cancelled open closes the budget again. All answer `FfiError.Cancelled`. A cancel after that step, or after the work finished, does nothing.
- A panic inside a session call reloads the budget from disk before the `Internal` error comes back, so memory always matches the file (R-REL-7).

## `CancelToken` (object)

| Call | Notes |
|---|---|
| `CancelToken()` | A fresh token for one call. |
| `cancel()` | Asks the work to stop. Safe to call any time, from any thread, more than once. |
| `isCancelled() -> Bool` | Whether `cancel()` was called. |

The pattern every wrapper uses:

```swift
let token = CancelToken()
return try await withTaskCancellationHandler {
	try await Session.importActualZip(zip: zip, intoDirectory: folder, cancel: token)
} onCancel: {
	token.cancel()
}
```

v9 adds category kinds and loans:
- `setCategoryKind(categoryId:kind:)` wraps veritas-engine's rules: a kind never crosses Actual's income flag (CLS-3.1) and an open goal's envelope stays `expense` (CLS-3.3), both `Invalid`. It reclassifies every row of the category, past and future, so confirm with `kindChangePreview` first.

When that group is hidden, `unhideGroup: true` (the user confirmed `kindCategoryPlan`'s prompt) unhides it and adds the category, its other categories keeping their own hidden flags; `false` is `Invalid` and writes nothing. `unhideGroup` has no effect on a visible group. One undo step; the new id is the `category` entity. `Invalid` while `kindTarget` isn't `.none`.
- `setLoanTerms(accountId:terms:)` replaces the loan's terms; a `nil` field clears it. An on-budget account or one set as an asset is `Invalid`, and so is a negative rate or payment, a day outside 1 to 31, or a payment past Actual's limit (`Overflow`). A blank lender is `nil`.
- `NewAccount` gains `loan: LoanTerms?` (default `nil`), so `createAccount` and `createBudget` save a loan or mortgage with its terms in the same step. Terms on any other kind are `Invalid`.
- `recordLoanPayment(payment: LoanPaymentDraft)` writes DEBT-6's rows. `LoanPaymentDraft { id, fromAccountId, loanAccountId, date, total, interest, escrow, fees, principalCategoryId, interestCategoryId, escrowCategoryId, feesCategoryId, notes, cleared }`, amounts positive cents. The payment is a split in `fromAccountId` (on budget) whose payee is the loan's lender (the live payee of that name, created if none; no payee without a lender), with lines in this order, each only when its part isn't 0: principal, a transfer to the loan in `principalCategoryId` (kind `debtPrincipal`), then interest, escrow and fees, each an expense line in its category (kind `expense`; escrow and fees need theirs). Principal is the remainder (DEBT-2.1); a payment smaller than its other parts is `Invalid` (DEBT-2.2), and so is a zero total. `id` naming a live split replaces that payment, its lines and their counterparts in the same step (A.2); otherwise it is the new payment's id, or `nil` for the core to pick. The payment is the first `transaction` entity. Actual reads the rows as a valid categorized split whose principal line counts as spending in its envelope (A.6).

v9 changes to v5's register commands: every amount a command writes must be within Actual's limit of 2^51 − 1 cents, either sign (`Overflow`); editing either side of a transfer now moves the other side's date too (R-XFER-3; Actual's server syncs only amount, account, payee, notes and schedule), and when the other side is a split line, its split and that split's other lines (and their own transfer partners) take the date; `cleared` stays each side's own, as in Actual. `deleteTransaction` on a row whose other side is a split line deletes that whole split with it, instead of Actual's unlink (R-XFER-3, DEBT-6 A.5; `counterpartParentId` tells the shell to confirm). When that split pays more than one loan, deleting any loan's side still deletes the whole payment, so the confirm must name every line it removes: fetch `registerRow(transactionId: counterpartParentId)` and list its `lines`, each other transfer line's loan included. `duplicateTransaction` copies an imported split that doesn't add up as it is, its stored error included, as Actual's Duplicate does. Closing an account counts only live rows, so an account whose only rows are lines of a deleted split is deleted, not closed.

v5 adds accounts, the register, reconciling and payees, each as Actual writes it (docs/actual-format.md §4):
- Accounts: `createAccount(account: NewAccount)` (at the end of its list, with its transfer payee and a starting-balance row; the id is the `account` entity), `renameAccount`, `moveAccount(accountId:beforeAccountId:)`, `setAccountOffBudget(accountId:offBudget:)` (the flag only, as Actual), `setAccountGroup(accountId:groupId:)`, `createAccountGroup(name:)`, `renameAccountGroup(groupId:name:)`, `moveAccountGroup(groupId:beforeGroupId:)`, `deleteAccountGroup(groupId:)` (its accounts leave it), `setAccountNote(accountId:text:)`, `closeAccount(accountId:transferToAccountId:categoryId:)` (an account with no rows is deleted instead; a non-zero balance needs `transferToAccountId` and moves there as a "Closing account" transfer, with `categoryId` on this side, which the UI asks for only when the money leaves the budget) and `reopenAccount(accountId:)`.
- Transactions: `addTransaction(transaction: TransactionDraft)`, `editTransaction(transactionId:transaction:)`, `deleteTransaction(transactionId:)`, `duplicateTransaction(transactionId:newId:)`, `setCleared(transactionIds:cleared:)` (reconciled rows are skipped; more than one row takes a `bulkEdit` snapshot first) and `unlockReconciled(transactionId:)`. `TransactionDraft { id, accountId, date, amount, payeeId, payeeName, categoryId, notes, cleared, splits }`, where `id` lets the app pick a new row's UUID so it can select it (`nil` lets the core pick; ignored by an edit), `payeeName` reuses a payee case-insensitively or creates one, and `splits` are `[SplitLineDraft { id, amount, payeeId, payeeName, categoryId, notes }]` that must add up to `amount` (`Invalid` otherwise, edge case 6); a line without a payee takes the parent's, as Actual's `makeChild` does; a line's `id` keeps its row on an edit, `nil` adds one, and a line left out is deleted. Adding runs the rules on the typed row and fills only what was left empty, or saves it as typed with `needsActual` when a rule can't run (D60, D64). A transfer payee makes the counterpart in the other account with WS-RULES' `transfers()`; edits follow Actual's transfer hooks (amount, notes, payee and account drive the other side; a non-transfer payee deletes it); on-budget to on-budget transfers lose their category. Saving a categorized row learns the payee's category as Actual's register does (`learn_categories`, §4.5), reading rules through the payee mapping. Editing never runs rules. Editing a split clears Actual's stored split error, since the lines must add up. An edit with `cleared: false` on a reconciled row is `Invalid`: as in Actual, a locked row is unlocked with `unlockReconciled` before it can be unchecked.
- Reconcile: `addReconcileAdjustment(accountId:statementBalance:)` (today, cleared, notes "Reconciliation balance adjustment", through the rules, marked as an adjustment, CLS-5) and `finishReconcile(accountId:statementBalance:)` (locks every cleared row when the difference is 0, and records `lastReconciled` either way).
- Payees: `renamePayee(payeeId:name:)` (not a transfer payee), `mergePayees(targetPayeeId:payeeIds:)` (transfer payees are left out and can't be a target; mappings follow the chain, transactions keep their ids; a `bulkEdit` snapshot is taken first), `setPayeeFavorite(payeeId:favorite:)` and `setPayeeLearnCategories(payeeId:learn:)`.

## Bills

v8, from WS-MAC-BILLS (R-BILL-1 to R-BILL-5). A bill is an Actual schedule and the rule it owns, written as Actual's schedule handlers write them, so it round-trips natively (R-BILL-4). Rules never show in the bill flow. `today` is the local date, `YYYY-MM-DD`.

| Call | Notes |
|---|---|
| `bills(today:) throws -> [BillSummary]` | Every live bill: active ones by next date, then paused and ended ones. `BillSummary { id, name, payeeId, payeeName, accountId, accountName, categoryId, scheduledAmount, isIncome, autoPost, nextDate, state, status, draft, customRule }`. `scheduledAmount` is what a post writes (the rounded middle of a range), negative for a bill and positive for income (R-BILL-5, `isIncome`). `state` is `active`, `paused` or `ended`. `status` is Actual's: `paid`, `due`, `upcoming` (within 7 days), `missed`, `scheduled` or `completed`. `draft` is the editor's model, or `nil` when Actual holds a schedule shape Veritas can't show: that bill is read-only, "Edit in Actual". `customRule` says its rule has conditions or actions the bill doesn't show; saving keeps them. |

`BillDraft { name, payeeId, accountId, amount, date, categoryId, autoPost }`:
- `amount` is `.exact(amount:)`, `.about(amount:)` (Actual matches within 7.5%) or `.between(low:high:)` (posts the rounded middle).
- `date` is `.once(date:)` or `.repeat(repeat: BillRepeat { start, interval, frequency, patterns, weekend, end })`. `frequency` is `daily`, `weekly`, `monthly` or `yearly`. `patterns` (monthly only; empty means the start's day) are `.day(day:)`, 1 to 31 or −1 for the last day, and `.weekday(weekday:nth:)`, `nth` 1 to 5 or −1 for the last. `weekend` is `nil`, `.fridayBefore` or `.mondayAfter`. `end` is `.never`, `.afterOccurrences(count:)` or `.onDate(date:)`.
- `categoryId` is kept as a plain `set category` on the bill's rule. A bill without `accountId` never posts. `autoPost` is Actual's `posts_transaction` (R-BILL-2).

Commands, each one undo step:
- `createBill(billId:bill:)` (`billId` picks the new id, or `nil` lets the core pick; it comes back as the `schedule` entity) and `editBill(billId:bill:)`. An edit rewrites only the schedule's four conditions and its plain amount and category actions, and resets the next date only when the date or account changed (D65). A name another bill has is `Invalid`, and so is anything Actual would mis-evaluate (R-BILL-4): a range with two equal amounts, patterns on a non-monthly bill, a day or week out of range, a fifth weekday mixed with other weekdays, a date Actual's API refuses, or a bill whose end comes before its first date. An unknown payee, account or category is `NotFound`; editing a read-only bill is `Invalid`.
- `pauseBill(billId:)` and `endBill(billId:)` are both Actual's Complete; only the label differs, kept in `veritas_schedule_meta`, and it never changes what posts. `resumeBill(billId:)` is Actual's Restart: the next date is reset from today. Resuming an active bill is `Invalid`.
- `payBill(billId:amount:date:)` is R-BILL-3's **Paid**: it posts the bill through its rules with the amount and date typed, which win over any rule action. A date before the window in which Actual counts the next occurrence paid also moves the bill on (a recurring bill to its next date, a one-time bill to completed), so Actual never shows it due again. A bill without an account is `Invalid`.
- `skipBill(billId:)` skips one occurrence; a one-time bill is `Invalid`. `postBillNow(billId:datedToday:)` is Actual's "Post transaction" (dated the next date) or "Post transaction today"; the next date moves at the service's next run, once Actual counts the bill paid.
- A post goes through the rules, and a transfer payee makes the other leg as Actual's `addTransactions` does. When a rule can't run in Veritas, Paid and Post now write nothing and fail with `Invalid` carrying the note (D60): for Paid on a due auto-post bill, the note says Actual will post it at its scheduled amount on its next open, so don't enter it there too.

The schedule service runs in `maintain(today:)`, once a day, the way Actual runs it on open: due and missed auto-post bills are posted (catching up missed occurrences one by one), paid recurring bills move on and paid one-time bills complete. It is gated by `metadata.json`'s `lastScheduleRun`: it runs only when that isn't `today`, and sets it to `today` after the commit, outside SQLite. A bill whose post meets a rule Veritas can't run (including its transfer leg's) is left to Actual whole, and then the day isn't marked done, so Actual's own service still posts it. The run is its own undo step; undoing it leaves `lastScheduleRun` alone. Creating, editing, pausing, ending or resuming an auto-post bill clears `lastScheduleRun` after the commit, outside undo, as Actual does, so the service runs again today. Restoring a snapshot clears it too, because a snapshot holds only the database while Actual's backup restore brings back the `metadata.json` it was taken with. Veritas and Actual opening the same budget never post a due bill twice.

## Rules

v8, from WS-MAC-BILLS (R-RULE-2, R-RULE-3). This is the sentence-style editor: *When imported payee contains "AMZN" → set payee to Amazon, set category to Shopping.* Rules are stored the way Actual's API stores them, with internal field names and the key order of `serialize()`. Any part a draft leaves unchanged keeps its stored text byte for byte.

| Call | Notes |
|---|---|
| `rules() throws -> [RuleSentence]` | The rules page's list (`ManageRules.tsx:145-160`): live rules ranked the way Actual runs them (stage pre, then default, then post; then specificity; then id). Rules of completed bills and rules Actual can't read (it drops them at load) are left out. `RuleSentence { id, stage, conditionsOp, conditions, actions, access, runsInVeritas }`. `access` is `.editable`, `.bill(scheduleId:)` (a rule with `link-schedule`, or one a schedule names; edit it through the bill) or `.editInActual(reasons:)` (shown read-only and kept byte-identical; `reasons` are noun phrases like "a template action", "split lines the sentence editor can't build" or "stored details the sentence editor can't keep"). `runsInVeritas` is false when Veritas can't evaluate the rule (R-RULE-3); rows it would touch then get "may need Actual". |
| `rulePreview(source:cancel:) async throws -> [RuleMatch]` | "Apply to existing". It finds the live rows that aren't split parents and that the conditions match, the way Actual's rule editor searches (its SQL evaluator, not the one rules run with), newest first. `source` is `.saved(ruleId:)` or `.draft(draft:)`, so an unsaved draft previews too. `RuleMatch { transactionId, parentId, date, accountId, amount, payeeId, categoryId, notes, changes, splitLines }`, `RuleSplitLine { amount, payeeId, categoryId, notes }` (the lines a split rule would make, in order) and `RuleFieldChange { field, before, after }`. `field` is a `RuleChangedField`: `account`, `date`, `amount`, `payee`, `category`, `notes`, `importedPayee`, `cleared`, `reconciled`, `schedule` or `deleted`. `changes` is what applying would write on that row, including the category Actual clears on an off-budget row or a new transfer. A payee the apply would create shows as `.text(text:)` with its name. A condition Veritas can't search for (a repeating date, `payee_name`, a regex it can't read the JS way), or actions it can't run, answers `Invalid`. |

Values:
- `RuleCondition { field: RuleField, op: RuleConditionOp, value: RuleValue }`.
- `RuleAction { op: RuleActionOp, field: RuleField?, value: RuleValue, splitIndex: UInt32 }`.
- `RuleDraft { stage, conditionsOp, conditions, actions }`. `RuleStage` is `pre`, `default` or `post`, and `RuleConditionsOp` is `and` or `or`.
- `RuleField`: `importedPayee`, `payee`, `payeeName`, `account`, `category`, `categoryGroup`, `notes`, `amount`, `amountInflow`, `amountOutflow`, `date`, `cleared`, `reconciled`, `transfer`, `parent`, and from v11 `saved`, a saved filter, for report and widget filters only (a rule draft with it is `Invalid`). `amountInflow` and `amountOutflow` are for conditions only; Actual stores them as `amount` with an option.
- `RuleConditionOp`: `is`, `isNot`, `contains`, `doesNotContain`, `matches`, `oneOf`, `notOneOf`, `hasTags`, `hasAnyTag`, `isApprox`, `isBetween`, `gt`, `gte`, `lt`, `lte`, `onBudget`, `offBudget`, and `and` (Actual's internal op, read-only).
- `RuleActionOp`: `set`, `prependNotes`, `appendNotes`, `deleteTransaction`, `setSplitAmount`, and `linkSchedule` (read-only). `field` is set only for `set`. `splitIndex` 0 is the transaction itself, and 1 and up number split lines.
- `RuleValue`:
  - `.id(id:)` is a payee, category, category group, account or schedule id; `nil` means empty.
  - `.ids(ids:)`, `.text(text:)`, `.texts(texts:)`.
  - `.amount(amount:)` is in cents. `.amountRange(num1:num2:)` holds `isBetween`'s two ends, in the stored order.
  - `.date(date:)` (`YYYY-MM-DD`), `.month(month:)` (`YYYY-MM`), `.year(year:)`.
  - `.bool(value:)`.
  - `.percent(percent:)`: a split line's share of what the fixed amounts leave.
  - `.nothing`: for `onBudget`, `offBudget`, `deleteTransaction` and a remainder split line.
  - `.raw(json:)`: stored JSON the sentence can't show, such as a repeating date or a template. It is never accepted in a draft.

What a draft accepts: at least one condition and one action, and each condition's op valid for its field, as Actual's `isValidOp` decides. The value must fit the op:
- `.id` for `is` and `isNot` on payee, account, category and category group.
- `.ids` or `.texts`, non-empty, for `oneOf` and `notOneOf`.
- Non-empty `.text` for `contains`, `doesNotContain`, `matches`, `hasTags` and `hasAnyTag`.
- `.amount` or `.amountRange` for amounts. Inflow and outflow don't take `isBetween`.
- `.date`, `.month` or `.year` for `is` on a date; `.date` alone for the date's other ops.
- `.bool` for flags.

Actions on the transaction itself (`splitIndex` 0) are `set` on `payee`, `payeeName`, `category`, `account`, `notes`, `importedPayee`, `amount`, `date`, `cleared` or `reconciled`, plus `prependNotes`, `appendNotes` (non-empty text) and `deleteTransaction`. A split rule builds its lines the way Actual's editor does:
- Number the lines from 1 with no gaps, and give each exactly one `setSplitAmount`. Its value is `.amount` (fixed), `.percent` (more than 0, at most 100) or `.nothing` (an equal share of the remainder; the last remainder line takes the rounding).
- A line may also `set` its `payee`, `category` or `notes`.
- A split rule can't also set `payeeName`, and linking a bill is refused. The rule written must also be one Veritas can run, so a regex it can't read the JS way is refused. An unknown payee, category, category group or account is `NotFound` (only in parts the draft changed). Everything else is `Invalid`, with a message for the person.

Commands, each one undo step:
- `createRule(draft:)`: the new id is the `rule` entity in the `Change`.
- `editRule(ruleId:draft:)`: items equal to stored ones keep their stored text, and an unchanged draft writes nothing. A bill's rule, an `.editInActual` rule or a rule Actual can't read is `Invalid`.
- `deleteRule(ruleId:)`: tombstones the rule. While any schedule names the rule it is `Invalid`, as Actual's `deleteRule` refuses.
- `applyRule(source:transactionIds:)`: "apply to existing" on the rows the person ticked. It runs only the rule's actions, overwriting what's there, as Actual's `rule-apply-actions` does, then the transfer hooks: setting a transfer payee makes the other leg, and a change on a transfer updates it. An off-budget row loses its category. The session snapshots first (`ruleApply`). A split rule makes each chosen row a split parent: its payee and category move to the lines, which are built and ordered as Actual's `makeChild` builds them. When the lines don't add up, the parent keeps Actual's split error. Split lines themselves only take the rule's other actions. A rule Veritas can't run, or a payee name two payees share, is `Invalid` and writes nothing (D60). A split parent is `Invalid`; apply to its lines. An unknown or deleted row is `NotFound`.

## Change events

`Change { entities: [EntityRef], everything: Bool }`. `EntityRef { kind, id, month }` names one row: `kind` is an `EntityKind`, `id` is absent only for a month's hold, and `month` is set for budget cells and holds. A change naming an account or transaction means the overview's balances changed. `everything` (after a restore, a reload, or the background check turning the budget read-only) means refetch every screen and `state()`.
