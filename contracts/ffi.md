# FFI surface (contract v5)

`veritas-ffi` is the only crate the apps link. It exports with UniFFI proc macros, and `cargo xtask bindings` generates the Swift module `VeritasCore`, with its C module `VeritasCoreFFI`, into `apps/macos/Packages/VeritasKit`. Swift never sees SQL, Actual column names or business rules (PLAN §6.1, Appendix C).

## Rules for every export

- Every export returns `Result<_, FfiError>` and goes through `guard`, which catches panics into `FfiError::Internal`. UniFFI turns an infallible export into `try!` in Swift, so a panic there would crash the app.
- Coarse calls only. The UI asks for whole screen models ("budget month 2027-03"), never one cell at a time (PLAN §6.5).
- Records are plain data. Money crosses as `i64` minor units, and VeritasKit formats it for display. Dates cross as `"YYYY-MM-DD"` strings, months as `Month`, and moments as UTC `"YYYY-MM-DDTHH:MM:SSZ"`.
- Long work (open, create, import, export, and later reports and forecasts) is `async` in Swift, runs on a core thread, and takes a `CancelToken`. UniFFI never cancels the Rust side of an `async` call, so cancelling the Swift task alone stops nothing. The caller makes a `CancelToken()` per call and calls `token.cancel()` from `withTaskCancellationHandler`. The work then stops before its one visible step: a cancelled create, import or export leaves nothing behind, and a cancelled open closes the budget again. All answer `FfiError.Cancelled`. A cancel after that step, or after the work finished, does nothing.
- A panic inside a session call reloads the budget from disk before the `Internal` error comes back, so memory always matches the file (R-REL-7).

## `CancelToken` (object)

| Call | Notes |
|---|---|
| `CancelToken()` | A fresh token for one call. |
| `cancel()` | Asks the work to stop. Safe to call any time, from any thread, more than once. |
| `isCancelled() -> Bool` | Whether `cancel()` was called. |

The pattern every wrapper uses:

```swift
let token = CancelToken()
return try await withTaskCancellationHandler {
	try await Session.importActualZip(zip: zip, intoDirectory: folder, cancel: token)
} onCancel: {
	token.cancel()
}
```

## `Session` (object)

One open budget folder. A second window or process on the same folder opens read-only (R-REL-6).

| `Session.createBudget(name:directory:format:options:cancel:) async throws` | A brand-new budget (R-IO-0, D52 to D56). `NumberFormat { currency, style, hideDecimals }`, where `style` is one of `commaDot`, `dotComma`, `spaceComma`, `apostropheDot` and `commaDotIn`. `NewBudgetOptions { retirement401k, hsa, accounts }`, where each `NewAccount { name, kind, startingBalance }` is in cents. | `perform(command:) throws -> Change` | Each `Command` is one SQLite transaction (R-REL-1) and one undo step (R-REL-5). v1 has `renameAccount(accountId:name:)`. v3 adds the budget's: `setBudget(month:categoryId:amount:)`; `moveBudget(month:amount:fromCategoryId:toCategoryId:)`, where a `nil` id is To Budget, never a transaction (R-BUD-4); `coverOverspending(month:categoryId:fromCategoryId:amount:)`, where `nil` covers all of it from To Budget or the whole overspend; `holdForNextMonth(month:amount:)` and `resetHold(month:)`; `setCarryover(month:categoryId:carryover:)`; and `setCategoryNote(categoryId:text:)`, where blank text removes the note (R-BUD-6). "Also move those" makes one budget move per later month, each with Actual's movement note (GOAL-7). v5 adds accounts, the register, reconciling and payees, each as Actual writes it (docs/actual-format.md §4):
- Accounts: `createAccount(account: NewAccount)` (at the end of its list, with its transfer payee and a starting-balance row; the id is the `account` entity), `renameAccount`, `moveAccount(accountId:beforeAccountId:)`, `setAccountOffBudget(accountId:offBudget:)` (the flag only, as Actual), `setAccountGroup(accountId:groupId:)`, `createAccountGroup(name:)`, `renameAccountGroup(groupId:name:)`, `moveAccountGroup(groupId:beforeGroupId:)`, `deleteAccountGroup(groupId:)` (its accounts leave it), `setAccountNote(accountId:text:)`, `closeAccount(accountId:transferToAccountId:categoryId:)` (an account with no rows is deleted instead; a non-zero balance needs `transferToAccountId` and moves there as a "Closing account" transfer, with `categoryId` on this side, which the UI asks for only when the money leaves the budget) and `reopenAccount(accountId:)`.
- Transactions: `addTransaction(transaction: TransactionDraft)`, `editTransaction(transactionId:transaction:)`, `deleteTransaction(transactionId:)`, `duplicateTransaction(transactionId:newId:)`, `setCleared(transactionIds:cleared:)` (reconciled rows are skipped; more than one row takes a `bulkEdit` snapshot first) and `unlockReconciled(transactionId:)`. `TransactionDraft { id, accountId, date, amount, payeeId, payeeName, categoryId, notes, cleared, splits }`, where `id` lets the app pick a new row's UUID so it can select it (`nil` lets the core pick; ignored by an edit), `payeeName` reuses a payee case-insensitively or creates one, and `splits` are `[SplitLineDraft { id, amount, payeeId, payeeName, categoryId, notes }]` that must add up to `amount` (`Invalid` otherwise, edge case 6); a line without a payee takes the parent's, as Actual's `makeChild` does; a line's `id` keeps its row on an edit, `nil` adds one, and a line left out is deleted. Adding runs the rules on the typed row and fills only what was left empty, or saves it as typed with `needsActual` when a rule can't run (D60, D64). A transfer payee makes the counterpart in the other account with WS-RULES' `transfers()`; edits follow Actual's transfer hooks (amount, notes, payee and account drive the other side; a non-transfer payee deletes it); on-budget to on-budget transfers lose their category. Saving a categorized row learns the payee's category as Actual's register does (`learn_categories`, §4.5), reading rules through the payee mapping. Editing never runs rules. Editing a split clears Actual's stored split error, since the lines must add up. An edit with `cleared: false` on a reconciled row is `Invalid`: as in Actual, a locked row is unlocked with `unlockReconciled` before it can be unchecked.
- Reconcile: `addReconcileAdjustment(accountId:statementBalance:)` (today, cleared, notes "Reconciliation balance adjustment", through the rules, marked as an adjustment, CLS-5) and `finishReconcile(accountId:statementBalance:)` (locks every cleared row when the difference is 0, and records `lastReconciled` either way).
- Payees: `renamePayee(payeeId:name:)` (not a transfer payee), `mergePayees(targetPayeeId:payeeIds:)` (transfer payees are left out and can't be a target; mappings follow the chain, transactions keep their ids; a `bulkEdit` snapshot is taken first), `setPayeeFavorite(payeeId:favorite:)` and `setPayeeLearnCategories(payeeId:learn:)`.

The session keeps the envelope sheet between calls and brings it up to date after each commit, undo and redo from the first month that changed (R-PERF-2). `budgetMonth`, `goals`, `goalClosePreview` and the budget commands all read it, so calling `budgetMonth` after every `Change` that names a budget cell, hold, transaction, category or group is cheap. `today` passed to any of these is also the date later commands plan against.

## Change events

`Change { entities: [EntityRef], everything: Bool }`. `EntityRef { kind, id, month }` names one row: `kind` is an `EntityKind`, `id` is absent only for a month's hold, and `month` is set for budget cells and holds. A change naming an account or transaction means the overview's balances changed. `everything` (after a restore, a reload, or the background check turning the budget read-only) means refetch every screen and `state()`.
