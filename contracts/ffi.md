# FFI surface (contract v22)

`veritas-ffi` is the only crate the apps link. It exports with UniFFI proc macros, and `cargo xtask bindings` generates the Swift module `VeritasCore`, with its C module `VeritasCoreFFI`, into `apps/macos/Packages/VeritasKit`. Swift never sees SQL, Actual column names or business rules (PLAN §6.1, Appendix C).

## Rules for every export

- Every export returns `Result<_, FfiError>` and goes through `guard`, which catches panics into `FfiError::Internal`. UniFFI turns an infallible export into `try!` in Swift, so a panic there would crash the app.
- Coarse calls only. The UI asks for whole screen models ("budget month 2027-03"), never one cell at a time (PLAN §6.5).
- Records are plain data. Money crosses as `i64` minor units, and VeritasKit formats it for display. v14: some widget values cross as `f64` minor units, where Actual's own figure is fractional or can be NaN or infinite (the summary card, the crossover card, the spending card's budget line and the Monte Carlo card); the shell rounds them only for display. Dates cross as `"YYYY-MM-DD"` strings, months as `Month`, and moments as UTC `"YYYY-MM-DDTHH:MM:SSZ"`.
- Long work (open, create, import, export, and later reports and forecasts) is `async` in Swift, runs on a core thread, and takes a `CancelToken`. UniFFI never cancels the Rust side of an `async` call, so cancelling the Swift task alone stops nothing. The caller makes a `CancelToken()` per call and calls `token.cancel()` from `withTaskCancellationHandler`. The work then stops before its one visible step: a cancelled create, import or export leaves nothing behind, and a cancelled open closes the budget again. All answer `FfiError.Cancelled`. A cancel after that step, or after the work finished, does nothing.
- A panic inside a session call reloads the budget from disk before the `Internal` error comes back, so memory always matches the file (R-REL-7).

## `CancelToken` (object)

| Call | Notes |
|---|---|
| `CancelToken()` | A fresh token for one call. |
| `cancel()` | Asks the work to stop. Safe to call any time, from any thread, more than once. |
| `isCancelled() -> Bool` | Whether `cancel()` was called. |

The pattern every wrapper uses:

```swift
let token = CancelToken()
return try await withTaskCancellationHandler {
	try await Session.importActualZip(zip: zip, intoDirectory: folder, cancel: token)
} onCancel: {
	token.cancel()
}
```

- `date` is `.once(date:)` or `.repeat(repeat: BillRepeat { start, interval, frequency, patterns, weekend, end })`. `frequency` is `daily`, `weekly`, `monthly` or `yearly`. `patterns` (monthly only; empty means the start's day) are `.day(day:)`, 1 to 31 or −1 for the last day, and `.weekday(weekday:nth:)`, `nth` 1 to 5 or −1 for the last. `weekend` is `nil`, `.fridayBefore` or `.mondayAfter`. `end` is `.never`, `.afterOccurrences(count:)` or `.onDate(date:)`.
- `categoryId` is kept as a plain `set category` on the bill's rule. A bill without `accountId` never posts. `autoPost` is Actual's `posts_transaction` (R-BILL-2).

v13 adds to `BillSummary`, each with a default so Swift that builds one still compiles:
- `amountKind: BillAmountKind?`: `.exact`, `.about` or `.between`, the op of the schedule's amount condition (`_amountOp`; `ScheduleAmountCell`, `SchedulesTable.tsx:66-147`). `nil` when the rule has no amount condition. It is set for read-only bills too.
- `readOnlyReason: BillReadOnlyReason?`: set exactly when `draft` is `nil`. `.missingRule` (no live rule; a tombstoned rule now counts as missing, so such a bill is read-only instead of failing on save), `.unreadableRule` (its conditions or actions aren't JSON arrays), `.noAmount` (no `amount` condition with `is`, `isapprox` or `isbetween`, `extractScheduleConds`, `lc/shared/schedules.ts:255-281`), `.unsupportedAmount` (the amount or a range end isn't a whole number of minor units), `.noDate` (no `date` condition with `is` or `isapprox`) and `.unsupportedDate` (a date that isn't `YYYY-MM-DD`, such as a month, or a RecurConfig the editor can't show). A bill whose rule is missing or unreadable is still listed: its status ignores linked transactions, `canSkip` is false and `paidTodayCounts` is false.
- `customParts: [BillCustomPart]`: what makes `customRule` true, empty exactly when it is false. `.extraConditions` (conditions besides payee, account, date and amount) and `.extraActions` (actions besides `link-schedule` and one plain `set category`).
- `lastPaidAmount: Int64?` and `lastPaidDate: String?`: the most recent live transaction linked to the bill, first in Actual's default transaction order (date newest first, starting balances last, `sort_order` newest first, then id; `lc/server/aql/schema/index.ts:278-285`). Split lines are left out, so a split payment counts whole. When the bill has an account, only rows in that account count, since a transfer bill's other leg links the bill too with the opposite sign. Both `nil` when nothing is linked.
- `canSkip: Bool`: whether **Skip** moves the bill. Actual offers "Skip next scheduled date" on every schedule that isn't completed (`SchedulesTable.tsx:189-194`), but `skipNextDate` (`app.ts:505-507`) writes only when `getNextDateAfter` (`lc/shared/schedules.ts:320-338`) finds a different date (`app.ts:253-281`). So it is false for a paused or ended bill, a one-time bill, a bill without a next date and the last occurrence of a bill that ends. `skipBill` succeeds on an active bill exactly when this is true.

v13 adds to `UpcomingBill` (defaults `nil`): `accountName`, `categoryName` (the bill's plain category; `nil` for a read-only bill, one without a category, or a deleted category) and `amountKind`. v15 adds `paidTodayCounts: Bool` (default `false`): `BillDetail.paidTodayCounts` for the bill, set only on its next occurrence, since Paid always pays the next one. When it is true the tray can offer "Post today" on an occurrence days out; when false, Paid today also moves the bill on.

v13 changes the range rule: a `BillAmount.between(low:high:)` is ordered by size, not sign. It is valid when `|low| < |high|`, so a bill's range stays negative with the smaller amount first, as in `(-4000, -4500)`, and an income range is positive, as in `(1000, 2000)`. `|low| > |high|` is `Invalid`, "Put the smaller amount first", and so are equal sizes with opposite signs. `low == high` is still "A range needs two different amounts". Actual's editor neither swaps nor refuses the ends: `BetweenAmountInput` keeps them as typed (`dc/components/util/AmountInput.tsx:246-273`), and Actual orders them only when it matches (`sortNumbers`, `lc/server/rules/condition.ts:326-330`). Its schedule list shows each end's size in stored order (`SchedulesTable.tsx:79-88`), so `(-4000, -4500)` reads "$40 and $45". A range Actual saved larger amount first now reads into `draft` smaller amount first, so it stays editable. It posts the same middle, and saving it writes `num1` as the smaller amount.

Commands, each one undo step:
- `createBill(billId:bill:)` (`billId` picks the new id, or `nil` lets the core pick; it comes back as the `schedule` entity) and `editBill(billId:bill:)`. An edit rewrites only the schedule's four conditions and its plain amount and category actions, and resets the next date only when the date or account changed (D65). A name another bill has is `Invalid`, and so is anything Actual would mis-evaluate (R-BILL-4): a range with two equal amounts, patterns on a non-monthly bill, a day or week out of range, a fifth weekday mixed with other weekdays, a date Actual's API refuses, or a bill whose end comes before its first date. An unknown payee, account or category is `NotFound`; editing a read-only bill is `Invalid`.
- `pauseBill(billId:)` and `endBill(billId:)` are both Actual's Complete; only the label differs, kept in `veritas_schedule_meta`, and it never changes what posts. `resumeBill(billId:)` is Actual's Restart: the next date is reset from today. Resuming an active bill is `Invalid`.
- `payBill(billId:amount:date:)` is R-BILL-3's **Paid**: it posts the bill through its rules with the amount and date typed, which win over any rule action. A date before the window in which Actual counts the next occurrence paid also moves the bill on (a recurring bill to its next date, a one-time bill to completed), so Actual never shows it due again. A bill without an account is `Invalid`.
- `skipBill(billId:)` skips one occurrence; a one-time bill is `Invalid`. `postBillNow(billId:datedToday:)` is Actual's "Post transaction" (dated the next date) or "Post transaction today"; the next date moves at the service's next run, once Actual counts the bill paid.
- A post goes through the rules, and a transfer payee makes the other leg as Actual's `addTransactions` does. When a rule can't run in Veritas, Paid and Post now write nothing and fail with `Invalid` carrying the note (D60): for Paid on a due auto-post bill, the note says Actual will post it at its scheduled amount on its next open, so don't enter it there too.

The schedule service runs in `maintain(today:)`, once a day, the way Actual runs it on open: due and missed auto-post bills are posted (catching up missed occurrences one by one), paid recurring bills move on and paid one-time bills complete. It is gated by `metadata.json`'s `lastScheduleRun`: it runs only when that isn't `today`, and sets it to `today` after the commit, outside SQLite. A bill whose post meets a rule Veritas can't run (including its transfer leg's) is left to Actual whole, and then the day isn't marked done, so Actual's own service still posts it. The run is its own undo step; undoing it leaves `lastScheduleRun` alone. Creating, editing, pausing, ending or resuming an auto-post bill clears `lastScheduleRun` after the commit, outside undo, as Actual does, so the service runs again today. Restoring a snapshot clears it too, because a snapshot holds only the database while Actual's backup restore brings back the `metadata.json` it was taken with. Veritas and Actual opening the same budget never post a due bill twice.

`ForecastProjection { scenarioId, name, months, horizons, eventsInThePast, goalEtas }`:
- `scenarioId` is `nil` and `name` is empty for the baseline.
- `months` holds 13 entries: the current month's remainder, then 12 complete months. Each is `ForecastMonth { month, knownNetIncome, baselinedNetFlow, scenarioNetIncome, netIncome, netWorth, bandLow, bandHigh }`, with `netWorth` at the month's end. v18: `bandLow` and `bandHigh` (default `nil`) are FC-4.2 step 5's band at that month, the same formula at every complete month `h` = 1 to 12, nothing interpolated, so draw the band through every month rather than straight segments between horizons. The first entry, the current month's remainder, has none (`nil`), and with no history every entry is `nil`.
- `horizons` covers FC-3's 3, 6, 10 and 12 months as `ForecastHorizon { months, month, netWorth, bandLow, bandHigh, accounts, netWorthDifference }`. The band is `nil` with no history. A what-if never moves the band's offsets, only the net worth they are added to (FC-3). A horizon's band always equals `months[horizon.months]`'s. v18: in a what-if, `netWorthDifference` (default `nil`) is its `netWorth` less the baseline's at the same horizon, and each of its `accounts` carries `difference`, that account's balance less the baseline's (FC-3's what-if difference): positive means the what-if leaves more, negative less, and a goal contribution alone differs by 0 everywhere (SN-5). Both are `nil` in the baseline's horizons and in `accountsToday`. Show these figures as sent; never subtract two projections in the shell.
- `eventsInThePast` lists the event ids the projection left out (D67).
- `goalEtas` is `[GoalEtaItem { goalId, name, status, remaining, pace, optimisticPace, pessimisticPace, historyMonths, historyLabel, onTrack, text }]`, one per goal that isn't closed (FC-6, R-FC-4). `status` is `.reached`, `.spent`, `.noHistory`, `.notAdding`, `.spendingRecorded` or `.eta(month:optimistic:pessimistic:)`, where `pessimistic` is `nil` at "no ETA at the slowest pace". `.spendingRecorded` (D77, FC-6 E-15, E-16) is an active goal in a budget without 2 places whose category has spending through the end of the current budget month, a purchase dated after `today` included (Actual's `available` reads every row in the month's envelope). Its `remaining` would mix scales, so `remaining` is `nil` (v16; it is set for every other status): its `text` is "No ETA: spending recorded" and replaces the whole line, like "No ETA: nothing is being added", with no range and `onTrack` `nil`. It applies to active goals only, and is checked before "no history", so a goal with no complete month of history and such spending reads "No ETA: spending recorded", not "No ETA yet". Reached and closed goals are untouched. A what-if never changes it. `text` is FC-6's line, such as "ETA March 2027, range March 2027 to May 2027". Paces and `remaining` are budget scale; `available` mixes scales in a 0-place budget (CLS-12.10). A what-if's goal contributions change only these (SN-5). `GoalSummary.pace` stays the Goals screen's line and agrees with the baseline's `goalEtas`.

`knownFlows` is `[ForecastFlow { date, dueNow, accountId, accountName, amount, kind, counterpartAccountId, categoryId, categoryName, billId, name, certainty }]`, by date:
- `kind` is `income`, `expense` or `transfer`. A transfer moves `counterpartAccountId` by `-amount` and leaves net worth alone. Loan principal is a transfer.
- `certainty` is `known` (exact bills and income, and loan payments with a known split) or `estimated` (About and Between amounts, and a loan split read from the amounts). The band never widens for an estimated amount (FC-4.1).
- `dueNow` marks an unposted occurrence dated before today, which counts in the current month (FC-2).
- A loan payment comes as its interest, escrow and principal flows, each with the bill's id.

`loans` is `[LoanForecast { accountId, name, estimatedFromAmounts, interestAssumedZero, notes }]` (FC-2): every loan whose payment the forecast splits into flows, in Actual's account order, so the shell can show which loans are forecast. A cleanly mapped loan with no fee is listed with `notes` empty and both flags `false`; a loan the forecast can't use is in `unforecast` instead, with its reason. `notes` holds, in order: "Estimated from the amounts" when `estimatedFromAmounts`; "No interest line on the last payment, interest taken as 0" when `interestAssumedZero` (the core sets the flag, so the shell never infers it); "Escrow taken from {category} {amount}", plus ", the same category as the interest" when the two share a category; and one "Not repeated: {category} {amount}" for each part that isn't repeated.

`unforecast` is `[UnforecastItem { billId, loanAccountId, name, reason }]`: a bill or loan the forecast couldn't use, listed, never dropped silently. `shortfalls` is `[ForecastShortfall { date, loanAccountId, loanName, uncovered }]`: a payment below its interest and escrow; warn that the uncovered part isn't recorded (DEBT-2.2, DEBT-2.6).

`ScenarioChange` uses Actual's sign. Its amounts are register scale, except a goal contribution, which is budget scale:
- `.oneTime(date:accountId:categoryId:amount:)`
- `.recurring(start:endMonth:cadence:accountId:categoryId:amount:)`. `cadence` is `.everyMonths(count:)` or `.everyWeeks(count:)`, anchored on `start` the way bills repeat. `endMonth` `nil` is open-ended.
- `.categoryPercent(categoryId:percentBp:startMonth:endMonth:)`
- `.incomeChange(accountId:categoryId:change:startMonth:endMonth:)`. `change` is `.amount(amount:)` or `.percent(percentBp:)`. A `nil` category means all income.
- `.goalContribution(goalId:amount:startMonth:endMonth:)`

A one-time transfer between two accounts (FC-3's planned asset purchase) waits for schema v2's counterpart column (D50).

Commands, each one undo step, writing only `veritas_scenario` and `veritas_scenario_event`:
- `createScenario(name:firstEvent:today:)`. The new id is the `scenario` entity. A blank name, or one another what-if already has (compared case-insensitively), is `Invalid`. v17: `firstEvent` (optional) is the what-if's first line, checked as `addScenarioEvent` checks one, in the same undo step; a refused line refuses the whole command and writes nothing. `today` is required when `firstEvent` is set (`Invalid` without it) and ignored otherwise.

- `deleteScenario(scenarioId:)` removes the what-if and its events.

An unknown or deleted account, category or goal is `NotFound`; an amount past 2^51 − 1 is `Overflow`.

`EntityKind.scenario` (v16) names a what-if, its events included.

## Rules

v8, from WS-MAC-BILLS (R-RULE-2, R-RULE-3). This is the sentence-style editor: *When imported payee contains "AMZN" → set payee to Amazon, set category to Shopping.* Rules are stored the way Actual's API stores them, with internal field names and the key order of `serialize()`. Values:
- `RuleCondition { field: RuleField, op: RuleConditionOp, value: RuleValue }`.
- `RuleAction { op: RuleActionOp, field: RuleField?, value: RuleValue, splitIndex: UInt32 }`.
- `RuleDraft { stage, conditionsOp, conditions, actions }`. `RuleStage` is `pre`, `default` or `post`, and `RuleConditionsOp` is `and` or `or`.
- `RuleField`: `importedPayee`, `payee`, `payeeName`, `account`, `category`, `categoryGroup`, `notes`, `amount`, `amountInflow`, `amountOutflow`, `date`, `cleared`, `reconciled`, `transfer`, `parent`, and from v14 `saved`, a saved filter, for report and widget filters only (a rule draft with it is `Invalid`). `amountInflow` and `amountOutflow` are for conditions only; Actual stores them as `amount` with an option.
- Amount signs (v13). `amount` compares Actual's signed amount in minor units: negative is money out, so "amount is -5000" matches a 50.00 payment. `amountInflow` takes a positive value and matches only money in, compared as it is. `amountOutflow` takes a positive value and matches only money out, compared as its absolute value, so "outflow is 5000" matches -5000. Both are stored as `amount` with `options: {inflow: true}` or `{outflow: true}` (`deserializeField`, `lc/shared/rules.ts:120-128`). When rules run, a 0 amount passes both sign checks (`lc/server/rules/condition.ts:255-266`), but `rulePreview` searches as Actual's rule editor does, where inflow needs more than 0 and outflow less than 0 (`lc/server/transactions/transaction-rules.ts:550-561`). So "outflow ≤ 0" previews no rows, yet it applies to a 0 row when rules run.
- `RuleSentence.billName` (v13, default `nil`): for a `.bill` rule, the schedule's name, `nil` when the bill has none or for any other rule. Actual's rules page describes the link as the payee and next date instead (`describeSchedule`, `dc/util/schedule.ts:210-219`).
- `RuleMatch.reconciled: Bool` (v13, default `false`): the row is reconciled. `RuleMatch.mayNeedActual: Bool` (v13, default `false`): the row's `transaction_meta.needs_actual` is set, so it carries "may need Actual".
- `RuleConditionOp`: `is`, `isNot`, `contains`, `doesNotContain`, `matches`, `oneOf`, `notOneOf`, `hasTags`, `hasAnyTag`, `isApprox`, `isBetween`, `gt`, `gte`, `lt`, `lte`, `onBudget`, `offBudget`, and `and` (Actual's internal op, read-only).
- `RuleActionOp`: `set`, `prependNotes`, `appendNotes`, `deleteTransaction`, `setSplitAmount`, and `linkSchedule` (read-only). `field` is set only for `set`. `splitIndex` 0 is the transaction itself, and 1 and up number split lines.
- `RuleValue`:
  - `.id(id:)` is a payee, category, category group, account or schedule id; `nil` means empty.
  - `.ids(ids:)`, `.text(text:)`, `.texts(texts:)`.
  - `.amount(amount:)` is in cents. `.amountRange(num1:num2:)` holds `isBetween`'s two ends, in the stored order.
  - `.date(date:)` (`YYYY-MM-DD`), `.month(month:)` (`YYYY-MM`), `.year(year:)`.
  - `.bool(value:)`.
  - `.percent(percent:)`: a split line's share of what the fixed amounts leave.
  - `.nothing`: for `onBudget`, `offBudget`, `deleteTransaction` and a remainder split line.
  - `.raw(json:)`: stored JSON the sentence can't show, such as a repeating date or a template. It is never accepted in a draft.

What a draft accepts: at least one condition and one action, and each condition's op valid for its field, as Actual's `isValidOp` decides. The value must fit the op:
- `.id` for `is` and `isNot` on payee, account, category and category group.
- `.ids` or `.texts`, non-empty, for `oneOf` and `notOneOf`.
- Non-empty `.text` for `contains`, `doesNotContain`, `matches`, `hasTags` and `hasAnyTag`.
- `.amount` or `.amountRange` for amounts. Inflow and outflow don't take `isBetween`.
- `.date`, `.month` or `.year` for `is` on a date; `.date` alone for the date's other ops.
- `.bool` for flags.

Actions on the transaction itself (`splitIndex` 0) are `set` on `payee`, `payeeName`, `category`, `account`, `notes`, `importedPayee`, `amount`, `date`, `cleared` or `reconciled`, plus `prependNotes`, `appendNotes` (non-empty text) and `deleteTransaction`. A split rule builds its lines the way Actual's editor does:
- Number the lines from 1 with no gaps, and give each exactly one `setSplitAmount`. Its value is `.amount` (fixed), `.percent` (more than 0, at most 100) or `.nothing` (an equal share of the remainder; the last remainder line takes the rounding).
- A line may also `set` its `payee`, `category` or `notes`.
- A split rule can't also set `payeeName`, and linking a bill is refused. The rule written must also be one Veritas can run, so a regex it can't read the JS way is refused. An unknown payee, category, category group or account is `NotFound` (only in parts the draft changed). Everything else is `Invalid`, with a message for the person.

Commands, each one undo step:
- `createRule(draft:)`: the new id is the `rule` entity in the `Change`.
- `editRule(ruleId:draft:)`: items equal to stored ones keep their stored text, and an unchanged draft writes nothing. A bill's rule, an `.editInActual` rule or a rule Actual can't read is `Invalid`.
- `deleteRule(ruleId:)`: tombstones the rule. While any schedule names the rule it is `Invalid`, as Actual's `deleteRule` refuses.
- `applyRule(source:transactionIds:)`: "apply to existing" on the rows the person ticked. It runs only the rule's actions, overwriting what's there, as Actual's `rule-apply-actions` does, then the transfer hooks: setting a transfer payee makes the other leg, and a change on a transfer updates it. An off-budget row loses its category. The session snapshots first (`ruleApply`). A split rule makes each chosen row a split parent: its payee and category move to the lines, which are built and ordered as Actual's `makeChild` builds them. When the lines don't add up, the parent keeps Actual's split error. Split lines themselves only take the rule's other actions. A rule Veritas can't run, or a payee name two payees share, is `Invalid` and writes nothing (D60). A split parent is `Invalid`; apply to its lines. An unknown or deleted row is `NotFound`.

## Change events

`Change { entities: [EntityRef], everything: Bool }`. `EntityRef { kind, id, month }` names one row: `kind` is an `EntityKind`, `id` is absent only for a month's hold, and `month` is set for budget cells and holds. A change naming an account or transaction means the overview's balances changed. `everything` (after a restore, a reload, or the background check turning the budget read-only) means refetch every screen and `state()`.
